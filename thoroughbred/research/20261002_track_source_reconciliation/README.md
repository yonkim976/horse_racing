# 주로환경 연구 원천 일치 여부 검증

작성일: 2026-10-02. 상태: **서울·부산 기존 연구 표본 연결 완료, 완전한 값 일치는 아님**. 운영 DB·원천 DB·모델·기존 보고서는 변경하지 않았다.

## 연구과제

2026-09-28 [주로 공통 잔차 최종 보고서](../../../research/track_common_residual_20260928/FINAL_REPORT_KO.md)가 참조하는 원천과 새 더러브렛 API 코어 DB가 같은 경주·말·기록·환경 정보를 갖는지 확인한다. 기존 보정 효과를 새 DB에서도 그대로 주장할 수 있는지, 후속 연구 전에 분리해야 할 차이가 무엇인지 판단한다.

**판정: 경주·말 연결과 대부분의 시간값은 일치하지만, 함수율과 소수 원문 기록이 달라 기존 연구 수치의 자동 승계는 보류한다.** 특히 불량 주로의 표본 부족 판단은 기존 함수율 결측의 영향을 받았으므로 새 자료로 다시 평가해야 한다. 이번 검증은 환경효과나 예측성능을 새로 추정한 실험이 아니다.

## 방법과 범위

- 기존 원천: `data/research/section_point_db_20260925/section_points_adjudicated.sqlite3`의 `common_point`, `data/horse_racing.sqlite3`의 경주·출전·완주·말·주로빠르기 정보.
- 새 원천: `thoroughbred/data/core_api_2010_20260929_v1/thoroughbred_core.duckdb`의 `confirmed_races`, `confirmed_runners`, `section_measurements_api`.
- 범위: **2018-01-01~2026-09-20, 서울(1)·부산(3)**. 제주는 새 더러브렛 DB의 대상이 아니므로 제외했다. 영천과 2018년 이전 자료도 기존 연구의 직접 대조 범위 밖이다.
- 기존 최종 보고서의 SQL 필터를 재현했다. 정상 착순 1~20, 양수 완주시간, 다섯 주로상태, S1F/G1F/G3F 자료를 가진 출전행이 기존 연구 표본이다. 새 자료는 같은 착순·완주·상태 기준을 사용하되 구간 결측이 있는 출전행도 보존했다.
- 키: **경마장·경주일·경주번호·공식 말 ID**. 내부 SQLite `horse_id`나 `race_entry_id`를 새 DB의 ID로 사용하지 않았다. 마번은 별도 대조했다.
- 시간은 정수 밀리초로 비교한다. 마지막200·600은 직접 막판시간을 우선하고 없으면 `완주시간 − 해당 누적시간`을 사용했다. 새 API의 `1F_G/3F_G`와 기존 `G1F/G3F closing`은 같은 의미로 대응한다. S1F는 기존 방식과 동일하게 누적시간을 썼다.
- 보고서와 동일한 물리 범위·구간 정합성 필터 전후를 각각 대조했다. 기존 전체시간 필터는 평균속도 10~20m/s이다. 이는 재현을 위한 기준이며 모든 오류를 걸러내는 기준은 아니다.
- DB는 SQLite `mode=ro`·`query_only`, DuckDB `read_only=True`로 열었다. 원천 3개 DB·기존 보고서·코어 매니페스트의 SHA-256이 검증 전후 동일했다. 차이가 있는 API 행은 보관 JSON 원문까지 대조했다.
- 기존 보고서 작성 당시의 불변 DB 스냅샷 해시가 보고서에 없으므로, 이번 결과는 **현재 남아 있는 참조 원천과 현재 코어 DB의 비교**다. 9월 28일 당시 DB의 모든 바이트와 동일하다는 검증은 아니다.

50개 차이를 보관 RPT에서 다시 파싱했으며 **50개 모두 기존 값과 일치**했다. 새 값은 보관 API 원문의 직접시간 또는 누적시간 차와 일치했다. 따라서 단순 단위 변환이나 이번 코드의 파싱 실수로 설명되는 차이가 아니다. 원문이 서로 다르며, 어느 쪽이 실제 경주기록을 더 정확히 반영하는지는 별도 판정할 일이다.

### 불량 주로 표본의 해석이 달라지는 부분

기존 연구의 `contrasts()`는 상태별 차이를 추정할 때도 **숫자 함수율이 있는 행만 사용**한다. 기존 정상완주 표본에서 불량 주로는 서울 4,059행·52일, 부산 3,014행·46일이다. 그러나 숫자 함수율이 있는 날은 서울 12일·부산 7일뿐이었다. 보고서에서 추가 기대시간·경주잔차 적격조건을 적용한 서울 11일·부산 7일은 이보다 더 좁은 표본이다.

기존 숫자 결측 5,862개 출전행은 **모두 불량 상태**였다. 보관 RPT 예시(서울 2018-05-06, 2023-12-16)는 `주로:불량`만 적고 숫자 %를 생략한다. 새 API는 이들에 숫자를 제공한다. 따라서 기존 보고서의 ‘불량 근거가 적다’는 문장은 그 연구의 선택된 표본에 대한 설명이며, 보유 경주 자체가 항상 적다는 뜻으로 확대하면 안 된다.

새 불량 문자열의 숫자는 서울 **20·23**, 부산 **16·20**을 포함한다. 서울 2023-12-16 1~4경주는 API 원문에서 23%로 기록된다. 부산 16%의 불량 표기는 위 상태·숫자 충돌 사례에 해당한다. **기존 원천의 ‘숫자가 모두 20’이라는 제한을 새 DB 전체의 제한으로 그대로 옮길 수 없다.** 다만 23%의 표본이 충분한지와 숫자 20의 산정·표시 관행은 별도로 확인해야 한다.

52일·46일은 이번 범위 전체의 원문 상태 기준 일수이며, 환경효과 추정에 쓸 수 있는 기대시간·잔차 적격 경주일 수를 뜻하지 않는다. 후속 연구에서 그 수를 다시 계산해야 한다.

### 주로빠르기

새 코어 DB의 관련 테이블·열을 조사했지만 기존 `race_passing_summaries.tempo_raw`에 해당하는 **경주 주로빠르기 지표는 없다**. 상태와 함수율 연구는 새 DB로 구성할 수 있지만, 기존 연구의 ‘빠르기만 / 둘 다 / 당일 잔차+빠르기’ 후보 전체를 새 DB만으로 그대로 재현할 수는 없다.

기존 주로빠르기를 별도 검증한 보조 스냅샷으로 연결하는 연구와, 새 API만으로 상태·함수율·공통 잔차를 연구하는 경로를 분리한다. 누락된 빠르기를 함수율이나 경주 전개 템포로 만들어 채우지 않는다.

## 이어서 검증할 부분

1. **원천·품질 계약:** 원문 상태, 숫자 함수율, 숫자로 유도한 상태를 구분한다. 70경주 상태 충돌, 서울 50시간 차이, 부담중량 3행을 예외 원장으로 남기고 제외·포함 기준을 고정한다. 새 DB 우선이라는 가정과 원문상 물리적 진실을 구분한다.
2. **기존 설정 재현:** 동일한 기간·Ridge 설정·다음 경주 검증으로 원천만 바꾼 비교를 먼저 한다. 공통 158,337행 고정 비교와 추가 191행 포함 비교를 나눠, 값 변경과 표본 추가의 영향을 분리한다. 2024~2026년은 이미 관찰한 후향 평가 기간이며 새로운 독립 홀드아웃이라고 부르지 않는다.
3. **함수율 비선형 차이:** 경기장·정확한 거리·네 목표별 구간/정수 %/완만한 비선형 함수를 비교한다. 숫자 결측 때문에 빠졌던 불량 경주를 복구한 뒤 표본 수·경주일 군집 불확실성을 다시 산출한다. 20% 이상을 실제로 얼마나 세분할 수 있는지 먼저 본다.
4. **공통 환경과 전개:** 초반·막판·전체를 별도로 추정하고 경주 구성·부담중량·기수·최근 폼의 영향과 하루 공통 변동을 분리한다. 시간 차이가 큰 서울 12경주는 해당 경주를 제외한 민감도 분석도 시행한다. 해당 경주가 자기 보정값을 만드는 데 들어가지 않게 한다.
5. **다음 경주 예측 검증:** 단순 기대시간이 기존 보정 후보보다 좋았던 이유를 검토한다. 기존 기대시간이 이미 직전 기록을 입력하므로, 직전 잔차를 다시 0.5만큼 더하는 것이 적절한지와 환경 보정의 효용을 분리한다. 잔차 반영률은 이전 기간 내부에서만 선택하고 평가 연도로 최적화하지 않는다.
6. **운영 목표와 연결:** 시간 일관성이 좋아지는지 확인한 후 우승·Top2·Top3·동반 후보·추천 5두에 실제로 도움이 되는지 별도 실험한다. 시간 MAE 개선을 착순 적중이나 수익 개선으로 간주하지 않는다. 기존 보정속도 피처에 중복 보정이 들어가지 않게 설계한다.

이 순서는 후속 연구 제안이다. 이번 작업에서 새 환경효과 계수 추정, 모델 학습, 운영 승격은 수행하지 않았다.

- `results/summary.json`: 원천 해시·기간·키·열별 일치·결측·유효 이력 수.
- `results/investigation.json`: API 원문 추적, 상태/숫자 충돌, 불량 표본, 경주불성립 판정, RPT 재파싱 결과.
- `results/*_differences.csv`, `*_by_year.csv`, `*_unmatched.parquet`: 행 단위 차이·연도별 집계·연결되지 않은 키.
- `results/api_band_percent_conflicts.csv`: 상태·숫자 구간 충돌 70경주와 원문 위치.
- `results/rpt_time_value_checks.csv`: 시간 차이 50개와 보관 RPT 값.
- `results/archived_api_value_checks.csv`: 원문 API 숫자/시간 7,585개 검증. **전부 통과**. API 0으로 인한 측정 결측도 정상적인 파싱 결과로 확인했다.
- `results/rpt_moisture_missing_examples.json`: 숫자 함수율을 생략한 보관 RPT 예시·해시.
- 원문 API 근거 JSONL와 대조용 Parquet 스냅샷은 로컬에 보존하고 Git에서는 제외한다.

코드 검사 및 집계 항등식 검사를 통과했다. 키 중복이면 분석을 중단하며, 각 비교 열의 일치·차이·결측 건수를 합하면 공유 키 수와 정확히 같다. 원문 대조는 추출 정확성 검증이지 실제 환경의 인과효과나 예측 시점 공개 여부의 증명이 아니다.
