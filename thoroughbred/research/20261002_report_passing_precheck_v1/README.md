## 조사 범위와 결론

연구 기준은 2010-01-01~2026-09-29, 서울·부산경남·영천의 더러브렛이다. 모델 개발은 2017년 이후다. 이번에는 원천 보유 현황·공식 API 과거 반환 여부·저장 설계만 확인했다. 연구 코어와 운영 DB·서비스는 변경하지 않았다.

**세 자료 모두 공식 API는 있지만 전 기간 원천을 모두 확보·검증한 상태는 아니다.** API의 연도별 반환 건수, 저장한 원문의 수, 예상 사건 대비 완전성은 각각 다른 항목이다.

## RPT의 처분표와 심판 전체 본문 구분

주 에이전트가 dacom11 파일 1,827개를 다시 읽고 처분표 제목 17,371개를 확인했다. 별도의 `심판사항`·`심판리포트`·`심판위원 Report` 제목은 검출되지 않았다. 서브에이전트도 처분표 셀에 나오는 `심판위원` 표현을 전체 서술 리포트와 구분했다.

- dacom11에는 `구분 / 출전번호 / 대상명 / 처분종류 / 처분내용 / 세부내용`이 있다. 처분 행이 있는 경주는 12,791개, 표는 있지만 기재 행이 없는 경주는 4,580개다. 이는 이 표에 기재된 내용의 상태이며 모든 제재의 부재를 확정한 것이 아니다.
- API215 `judgement`에는 출발·접촉·진로 변경·주행 반응 등의 서술이 들어간다. 성적표 처분표를 이 전체 본문으로 대체하지 않는다.
- dacom11/API 리포트 어느 쪽이든 로컬 근거가 있는 합집합은 20,390경주다. **이 수치는 전체 심판 서술 리포트가 있는 경주 수가 아니다.**
- dacom11은 2015~2024년과 2026년 일부 날짜에 있다. 2025년 원문은 해당 대량 폴더에 없다. 보존 API는 2025~2026년 자료여서 서로 다른 기간을 보완한다.
- 주행심사 dacom23 원문은 1,628파일이고 저장경로 날짜는 2010-01-08~2026-09-17이다. 주행심사 심판사항은 정식 경주 리포트와 별도 자료군이다. 이 파일 수로 심사 전체 사건·제재가 모두 확보됐다고 판단하지 않는다.

## 저장 제안

### 1. 공통 원문과 사건 연결

API 항목·페이지와 RPT 원문·줄번호·원문 해시·수집 시각을 먼저 보존한다. 원문 관측의 식별자는 파일·페이지·행 위치를 포함한다. 같은 경주·대상·처분 종류가 반복됐다는 이유만으로 실제 처분 하나라고 합치지 않는다. 게시 시각·수집 시각·사건일·효력 시작/종료일은 별도다.

경주의 공통 연결 키는 **실제 경주장 × 경주일 × 경주번호**다. 저장경로의 meet와 실제 경주장을 분리한다. 예를 들어 `dacom11/meet=3/.../20260913dacom11.rpt`의 6경주는 본문에 `(영천)`이라고 명시되어 있다. 이는 본문 근거로 영천 경주와 연결하며 경로 meet=3은 출처 속성으로 남긴다. 이름만으로 말·관계자 ID를 만들지 않는다.

취소·불성립 보고서는 원문과 해당 계획 경주에 남긴다. 통과조 값이 없다는 이유로 리포트를 삭제하지 않는다. 로컬 부산경남 2025-12-26 6경주 API215는 불성립 경주 리포트로 확인됐다.

### 2. 심판 리포트

- `steward_report_observations`: 한 경주의 각 원문 수집본. `judgement`, `addJudgement`, `jkChange`, 위원·날씨·출처를 보존한다.
- `steward_event_evidence`: 후속 추출 시 한 사건·언급 근거 단위. 사건 유형, 관련 말·기수, 원문 문장/위치, 확정 여부, 추출 규칙 버전을 둔다. 한 문장에 여러 말이 나오면 연결 관계를 별도 행으로 둔다.
- 원문 관측과 구조화 사건을 분리한다. 기수 진술·추정 의견을 공식 처분이나 확정 원인으로 바꾸지 않는다. 첫 적재에서는 자유 서술 전체를 유지하고 사건 추출은 별도 검증한다.

### 3. 제재·처분

- `sanction_observations`: API180_1 항목과 RPT 처분표의 각 원문 행. API는 `gubun`, `prNo`, `prName`, `chulNo`, `kind`, `reason`, `fine`, `stDate`, `spDate`, `etlTime` 등 원문 값과 타입을 유지한다.
- `sanction_decisions`: 대조 후 확인된 **대상별 처분 한 건당 한 행**. 대상 유형·공식 ID, 처분 종류·사유, 금액과 단위, 효력 기간, 관련 경주/심사, 판정 근거를 둔다. 하나의 경주에 여러 처분을 허용한다. ID·단위·효력일을 확인하지 못하면 결측과 원문을 남긴다.
- `sanction_source_links`: 하나의 처분과 API·RPT·리포트 문장의 다중 근거 관계. 정확히 같은 처분인지 확정하기 전에는 후보로 둔다. 반복 수집, 사후 정정, 기간 변경을 구분한다.
- 처분 종류가 `주행심사`·`출발심사`인 것은 심사 요구의 근거다. 실제 심사 시행·합격 여부는 별도 심사 사건에서 확인하며 요구 처분만으로 시행 기록을 만들지 않는다.

### 4. 통과조

- `passing_group_observations`: API303의 경주별 원문 행과 RPT의 인쇄 지점명·해당 문자열을 보존한다. API의 3F/4F 경주 통과시간·주로빠르기도 말별 구간값과 구분한다.
- `race_passing_groups`: **경주 × 지점당 한 행**, `notation_raw`와 지점 대응 규칙 버전·선택 원천·판정 근거를 둔다. 괄호·쉼표·`^`·`-`·`=`·`≡`를 그대로 보존한다.
- 기호 문법을 검증한 뒤 필요하면 지점 내 그룹과 출전번호 구성원을 파생한다. 문자열의 숫자는 그 경주의 출전번호이며 말 ID가 아니다.
- 서울 2020~2021의 API 코너 열과 인쇄 지점명 대응이 어긋났던 기존 근거가 있으므로 그 기간은 RPT 인쇄 라벨과 재대조한다. 원문 API 값을 덮어쓰지 않고 충돌 원장과 지점 대응 판정을 남긴다. 없는 지점이나 취소·불성립 경주의 값을 만들지 않는다.

### 5. 커버리지

예상 경주/심사마다 `source_present`, `not_collected`, `source_response_empty`, `official_blank`, `source_conflict`, `nonexecuted` 등을 구분한다. 제재 원천은 해당 경주에서 제재가 있을 때만 행을 반환할 수 있으므로 전체 경주 대비 제재 행 수로 완전성을 판정하지 않는다. API 페이지 완료와 실제 제재 전체의 완전성도 구분한다.

## 권장 작업 순서

1. 제재 API180_1과 통과조 API303의 2010년 이후 전 페이지 원문을 수집하고, API215도 전 기간 반환 원문과 정상 빈 응답을 보존한다.
2. 경주·심사·취소/불성립 원장과 키별 대조를 수행해 자료군별 공백을 확정한다. RPT 처분표와 통과조 인쇄 라벨을 추출·대조한다.
3. 구조화 제재·지점별 통과조를 적재한다. 심판 서술은 원문 적재 후 사건 유형별 표본·전수 규칙 검증을 거쳐 별도로 추출한다.
4. 심판 전체 본문의 과거 공백은 다른 공식 보관 원천의 존재를 조사한다. 처분표를 전체 본문으로 재분류해 완료 처리하지 않는다.
