# 제주 출발조교 홈페이지 기준 적재

2026년 10월 1일 사용자의 지시에 따라 출발조교는 공식 제주 홈페이지 기록을 기준으로 제주 전용 SQLite DB에 적재한다. API22 원문은 삭제하거나 덮어쓰지 않고 홈페이지 기록과의 대조 근거로 보존한다. 일별조교 API18은 이 출발조교 적재의 대상이 아니다.

## 범위와 저장 위치

대상 DB는 `../../data/jeju_native_core.sqlite3`다. 보유 API22에 기록된 2007-10-17부터 2026-09-27까지의 2,529개 날짜를 공식 홈페이지에서 전부 조회했다. 이는 해당 API 날짜 집합의 홈페이지 재수집이며, 홈페이지 전체 과거 달력이나 API가 비어 있는 날짜를 탐색한 결과는 아니다. 조회 실패와 파싱 실패는 없었다.

| 항목 | 건수 |
|---|---:|
| 홈페이지 원문 날짜 | 2,529 |
| 제주 경주장 전체 홈페이지 행 | 295,470 |
| API42 보유 제주마 4,617두 명단에 연결된 행 | 190,842 |
| 연결된 제주마 | 4,476 |
| 경주 상한 2026-09-19까지 분석용 조회 행 | 190,790 |
| 그 이후 별도 보관 행 | 52 |
| 제주마 행 중 400M 출발지점 | 176,102 |
| 제주마 행 중 800M 출발지점 | 14,740 |

홈페이지 원문 104,628행은 이번에 품종을 확인한 보유 ID 명단 밖이다. 원문 관측으로 보관하고 제주마 조회에서는 제외한다. 이를 전부 한라마로 확정한 것은 아니다.

## 연결과 중복 기준

홈페이지 마명 링크의 `goPage1(hrNo)`는 공식 말 프로필의 `hrNo`로 연결된다. 이 ID를 API42 제주마 프로필의 말 ID에 직접 연결한다. 현재 이름이나 당시 소속조로 말 ID를 추정하지 않는다.

- 홈페이지의 서로 다른 행은 같은 말·날짜·기승자·비고라도 각각 유지한다. 특히 400M·800M 출발지점의 기록은 별도 행이다.
- 같은 원문의 재적재는 `홈페이지 artifact ID + source_row_no`로 막는다. 내용 해시로 유일화하지 않는다.
- 보유 API22에는 조교장소가 없다. 홈페이지 장소를 API22 원문에 소급 기입하거나 API 두 item과 웹 두 행의 순번을 임의 대응하지 않는다.
- API22 대조는 같은 말 ID·날짜 전체 item에 대해 원문 페이지 SHA·페이지 번호·item 순번·필드 차이를 기록한다. API에 행이 없거나 내용이 달라도 홈페이지의 공식 ID가 제주마 프로필에 연결되면 홈페이지 기록을 유지한다.
- `note_raw`의 공란이나 API의 '-'를 양호로 바꾸지 않는다. 출발조교 시행시각·등록시각은 이번 원문에도 없으며 다른 일별조교 시각으로 대체하지 않는다.
- 이 행 수는 홈페이지 기록 행 수다. 시행 횟수 정의나 당시 공개시각을 확정한 값은 아니다. 모델 입력 자동 반영을 하지 않는다.

## 전체 대조에서 확인한 차이

2024-01-17 API와 홈페이지 모두 총 139행이다. 그러나 48개의 말 ID별 행 수가 다르다. API 과다 24두·27행과 홈페이지에만 있는 24두·27행이 상쇄된다. 총 행 수 일치만으로 정합성을 확인하면 안 된다.

별마로 3103304, 서부검객 3102101, 아연로 3103797은 각 API 4행 대신 홈페이지 400M·800M의 2행을 정규 자료로 저장한다. 같은 날짜 나머지 API 과다 21두는 각 API 2행 대신 홈페이지 1행을 사용한다. 홈페이지에만 있는 제주마 24두·27행도 공식 ID에 연결해 저장한다. API 원문은 모두 그대로 보존한다.

2016-03-13은 API 177행과 홈페이지 176행이며, 차이는 보유 제주마 ID 명단 밖의 1015842 한 행이다. 해당 말의 마종이나 누락 원인은 이번 작업으로 확정하지 않는다. 다른 날짜의 말 ID별 행 수는 전수 대조에서 일치한다. 필드 값·필드 존재 차이는 별도 evidence로 보존하며, 행 수 일치가 필드 전체 일치를 뜻하지 않는다.

## DB 객체

- `website_training_artifacts`: 조회일, URL, 조회시각, 성공 상태, 원문 HTML 경로와 SHA, 수집 원장 SHA를 보존한다. `collection_directory + html_relative_path`로 원문을 찾는다.
- `starting_training_website_rows`: 제주 경주장 전체 홈페이지 관측과 원문 행 순번, 소속조, 조번, 당시 화면 마명, 기승자, 장소, 비고, 말 ID 및 API22 대조 근거를 저장한다. 원문 모집단 밖의 말은 제주마 연결 상태를 부여하지 않는다.
- `starting_training_website_rows_latest`: 날짜별 최신 성공 artifact의 제주마 연결 행을 조회한다. 실패·빈 응답이 이전 성공 자료를 덮어쓰지 않는다.
- `starting_training_website_rows_analysis_2026`: 최신 성공 자료를 2026-09-19까지 자르고 `horse_analysis_2026`과 동일한 최신 프로필 선택 순서와 2026년 나이 계산식을 사용한다. API42 관측을 간결하게 조회해 말 ID로 연결한다. 표시명은 `current_horse_name`, 나이는 `current_horse_age_2026`, 기준연도는 `current_horse_age_reference_year=2026`이다. 당시 화면 마명은 `horse_name_raw`로 보존한다. 2026년 기준 나이는 조교 당시 나이가 아니다.

manifest `trainer_no`와 저장 열 `trainer_no_raw`는 화면의 **조번**, 즉 소속조 안의 말 번호다. 조교사 ID가 아니다. 조회 뷰의 별칭 `stable_horse_number_raw`를 사용한다.

```sql
SELECT training_date, horse_id, current_horse_name,
       current_horse_age_2026, affiliation_raw, stable_horse_number_raw,
       rider_raw, location_raw, note_raw
FROM starting_training_website_rows_analysis_2026
WHERE horse_id = '3103304'
ORDER BY training_date, source_row_no;
```

경주별 피처를 만들 때는 기존 [조교 입력 계약](<../../docs/JEJU_TRAINING_API_INPUT_CONTRACT_2026-10-01.md>)의 예측시점·공개시각·결측 제한을 유지한다. 출전행에 조교 원행을 직접 다대다 연결하지 않는다.

## 재현과 검증

`collection/collection_manifest.json`과 `collection/html/`에 원문과 조회 근거가 있다. 수집 코드, 읽기 전용 전수 대조 코드와 Luna xhigh가 작성하고 root가 검토한 적재 코드도 이 폴더에 보존한다. 적재기는 네트워크를 호출하지 않으며 원문 SHA를 확인한 뒤 실행한다.

root의 별도 파서가 전체 홈페이지 295,470행의 말 ID와 여섯 출력 열을 다시 추출해 수집 원장과 일치함을 확인했다. 실제 DB 적용 전 SQLite 복사본에서 2024-01-17, 전체 적재, 같은 원장의 재적재를 검증했다. 재적재의 추가 artifact와 행은 각각 0개였다. 실제 적용은 SQLite 백업 후 DDL과 INSERT를 한 트랜잭션으로 실행한다.

실제 적용과 검증의 확정 결과는 `production_apply.json`, `production_verification.json`, `stage_replay_v2.json`, `application_manifest.json`을 따른다. 기존 경주·심사·프로필 테이블의 행 수와 정의, 신규 홈페이지 행 전수 일치, 최신 이름·2026년 나이, FK와 SQLite integrity를 확인한다.

### 구현 검토 중 수정 사항

초기 v1 분석 뷰의 프로필 원천 조인이 수 분 걸리는 SQLite 조회 계획을 만들었다. root가 이 문제를 확인하고 v2에서 같은 최신 프로필 선택 순서와 나이 계산식을 API42 관측 테이블에 직접 적용했다. 기존 코어 분석 뷰는 변경하지 않았다. 초기 읽기 검증과 재적재를 동시에 실행한 시도는 읽기 잠금으로 실패해 중단했으며, 이후 순서대로 실행한 v2 재적재와 독립 검증이 통과했다. 실패한 시도는 임시 DB에서만 있었고 실제 DB에는 검토한 v2를 적용했다.

이전 `20261001_training_audit/audit_summary.json`의 미적재 표시는 그 감사 시점의 스냅샷이다. 현재 DB 상태를 판단할 때는 이번 적용 원장과 새 홈페이지 테이블·뷰를 조회한다. `api_records.record_type`에 조교가 없다는 것만으로 홈페이지 조교도 미적재라고 판단하지 않는다.
