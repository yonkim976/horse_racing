# API 통과착순 원문과 제주 경주결과 후보 연결

기준일: 2026-09-30 · 원천: 보존된 KRA OpenAPI 응답만 사용 · 새 API 호출 및 TXT/RPT 사용 없음

아래 후보 9,513경주·92,695행 집계는 2026-09-30 [재노출 행 삭제](<../../maintenance/zero_time_cleanup_20260930/README.md>) 전 스냅샷이다. 현재 후보는 9,494경주·92,513행이다. API 원문과 API303 적재행은 보존했다.

후속 [홈페이지 사유 확인](<../20260930_zero_time_cause_audit/README.md>)으로 이 문서의 `사유 미확정 76경주` 중 69경주·650행의 명시적 취소 사유가 확인됐다. 나머지 7경주·30행은 [2026-10-01 사용자 확인](<../20261001_user_cancellation_confirmation/README.md>)에 따라 취소 확인·사유 미표시로 반영했다. 현재 취소 여부 미확정은 0경주다.

API303의 공식 OpenAPI 명은 `한국마사회_경마코너별통과순위_주로빠르기`다. 공식 설명의 서울·제주 필드 매핑은 `corner_1`~`corner_4`=1~4코너, `corner_7`=S-1F, `corner_8`=G-1F이며, `corner_5`, `corner_6`, `corner_9`는 사용하지 않는다고 표기한다. 이 정의는 [공공데이터포털 API 명세](https://www.data.go.kr/data/15119851/openapi.do)를 따른다.

## 연결 구조

말별 통과착순은 API4_3 경주결과 원문에서 직접 가져온다. 후보 뷰 `jeju_race_population_candidate_passing_orders`는 같은 `api_record_id`의 원문에서 다음 필드를 노출한다.

`sjS1fOrd`, `sjG1fOrd`, `sjG3fOrd`, `sj_1cOrd`, `sj_2cOrd`, `sj_3cOrd`, `sj_4cOrd`

각 값은 `api4_3_*_raw`로 그대로 보이며 JSON 타입, 행 payload SHA-256, 원문 페이지 SHA-256과 경로도 함께 조회할 수 있다. 숫자 0은 0으로 유지한다. 0을 결측, 비적용 또는 상태 코드로 재해석하지 않는다.

API303 `/API303/corner_rank`는 경주당 한 행이며 말 ID가 없다. `api303_corner_rank_rows`는 이 원문 필드와 날짜·제주장 요청 코드 2·경주번호를 저장한다. `jeju_race_candidate_passing_with_corner_rank`는 API4_3 말별 결과와 API303 경주별 원문을 `(race_date, meet_code, race_number)`로 연결한다. API303의 `*_raw` 값과 `*_json_type`은 정규화용 열이 아니라 보존 payload에서 읽어 JSON의 문자열·정수 타입 차이도 유지한다. 이 조인은 경주 수준 대조이며 API303의 원문 값을 특정 말에 귀속하지 않는다. 구간기록 API6_1은 다른 endpoint와 필드 구조를 가지므로 이번 API303 테이블에 합치지 않았다.

`jeju_race_candidate_corner_rank_coverage`에서 다음 상태를 따로 본다.

- `api303_present`: API303에 해당 경주 행이 있는가.
- `api303_has_corner_order_content`: `corner_1`~`corner_9` 중 적어도 하나가 빈 값, `-`, `X` 이외인가. 이는 일관된 유효성 판정이 아니라 원문 문자열 존재를 요약하는 규칙이다.
- `api303_has_nonzero_passing_time`: 3F/4F 중 적어도 하나가 빈 값, `0:00.0`, `0:00` 이외인가.

따라서 API303 행 존재와 실제 숫자가 있는 코너 문자열 존재는 별도 상태다. 원문 key 부재·JSON null·빈 문자열·0도 서로 합치지 않는다.

## 적재와 교차 검증

전기간 API303 보존본은 2002–2026년 25개 연도 partition, 25페이지, 19,933행이다. 각 페이지의 바이트 수·페이지 번호·`totalCount`·날짜 연도·SHA-256을 확인했다. 19,933행 모두 고유한 `(날짜, meet=2, 경주번호)`이며 중복은 0건이다. 각 행은 원본 API 필드를 `api_records.payload_json`에 보존하고 payload SHA-256과 페이지 source artifact SHA-256으로 추적한다.

| 교차 집합 | 경주 수 |
|---|---:|
| API4_3 경주결과 키 | 20,117 |
| API303 경주 키 | 19,933 |
| 양쪽에 존재 | 19,933 |
| API4_3에는 있고 API303에는 없음 | 184 |

원천 공백 184경주 중 180경주는 API4_3에 있는 모든 말의 완주시간도 0이다. 나머지 4경주는 2026-07-07 1~4R로, 완주시간은 양수지만 말별 통과순위는 모두 0이다. 후속 [원인 감사](<../20260930_zero_time_cause_audit/README.md>)에서 이 4경주가 2026-04-11 제주 1~4R의 출전집합·착순·완주시간을 그대로 다시 노출한 자료임을 확인했다. 후보 32경주 목록은 JSON 보고서에 날짜·경주번호·후보 행 수와 함께 들어 있다. 이 후보 32경주 중 28경주·233행은 완주시간이 모두 0이고, 4경주·40행은 양수 완주시간과 0인 통과순위를 가진다.

후보 9,513경주 중 API303 원문 코너 문자열에 값이 있는 경주는 9,347, 행은 있으나 모든 코너 칸이 빈 값·`-`·`X`인 경주는 134, API303 행 자체가 없는 경주는 32다. 이 중 결과 API4_3 전 행의 완주시간이 0인 경주는 162개·1,535행(코너 placeholder 134경주와 원천 공백 28경주)이고, 나머지 원천 공백 4경주는 양수 완주시간이 있다. 후속 원인 감사에서 71경주·713행은 공식 취소 또는 경주불성립 근거, 15경주·142행은 이전 경주 출전집합의 다른 날짜 재노출, 76경주·680행은 사유 미확정으로 나뉘었다. 예를 들어 코너 문자열은 있으나 3F/4F 시간이 `0:00.0`인 후보 경주 598개는 모두 400m이고, 이들의 API4_3 5,535개 완주 행에서 3C·4C 순위도 0이다. 400m에서 해당 코너 지점이 비적용일 수 있으므로 이 0을 오류로 세지 않는다.

반대로 API303의 3F/4F 시간은 양수인데 코너 문자열이 전부 placeholder인 후보는 2018-04-28 제주 6R 1경주(10행)다. API303의 시간과 코너 문자열은 서로 독립적으로 확인한다.

2026-07-07 제주 1~4R은 API303 자료가 없다. API4_3 후보 40행은 1,000m 또는 1,110m 경주이고 완주시간은 양수지만 일곱 말별 통과순위가 모두 0이다. 후속 원인 감사에서 40행 모두가 2026-04-11 제주 1~4R의 말 ID·마번·착순·완주시간과 일치함을 확인했다. 7월 7일은 [2026년 제주 경마 시행계획](https://race.kra.co.kr/down/raceplan2026_jeju.pdf)의 시행 요일도 아니다. 이상 행은 보존한 API4_3 응답 자체에 있어 로컬 파서가 만든 것은 아니며, API 제공 시스템 내부의 생성 경로는 미확인이다.

2026-03-20 8R, 03-21 6R, 04-04 6R은 API303 행이 있으나 20개 경주 모두 `corner_1`~`corner_4`·`corner_7`·`corner_8`이 `-`, 3F/4F가 `0:00.0`, `tempo` key가 없다. 이 경주들의 API4_3 말별 완주시간도 0이고 결과 `ord`는 `99`, 말별 통과순위 필드 `sj*Ord`는 0이다. `ord=99`는 원문 결과 순위 코드이며 상태명으로 취급하지 않는다. 다만 별도 근거로 3월 20~21일은 [한국마사회 발표](https://www.newsnjeju.com/news/articleView.html?idxno=267595)에서 전면 취소를, 4월 4일 6R은 API215 심판사항에서 잔여 경주 취소를 확인했다.

## 과거·현재 API 필드 형태

API303의 필수 key는 `rcDate`, `rcNo`, `meet`, `corner_1`~`corner_9`, `passtime_3f`, `passtime_4f`였고 이 14개는 모든 적재 행에 있었다. `tempo`는 선택 필드다. 19,933행 중 241행에서 key 자체가 빠졌으며, 결측은 SQL에서 `tempo_raw=NULL`로 표시하되 원본 payload의 key 부재도 보존했다. 연도별 key 구성과 필드 값 형태는 같은 디렉터리의 `api303_corner_rank_ingest_report.json`에서 확인한다.

2002년에는 비어 있지 않은 코너 필드의 분포와 원문 표기가 후대와 다르다. 공식적인 코너 번호 매핑은 위 명세를 따른다. `corner_1/2/3/4/7/8`의 비-placeholder 원문은 각각 437/207/225/429/228/432경주다. 코너 열은 문자열뿐 아니라 정수도 포함한다. 예를 들어 2002-08-24 5R의 `corner_1`과 `corner_8`은 JSON 정수 `2435671`이다. 이 값을 다른 필드 의미로 바꾸지 않고 원문 타입 그대로 보존한다. 또 2002-07-28 1R은 공식 매핑상 1코너와 G-1F 열에 원문이 있고, 3·4코너 열은 `-`인데, API4_3 말별 `sj_3cOrd`/`sj_4cOrd`에는 양수가 있다. 이 경주는 경주 단위 API303 원문과 말 단위 API4_3 필드를 각각 보존하며, 코너 열 번호가 역사적으로 이동했다고 해석하지 않는다. 2003년 이후에는 `corner_3/4/7/8`에 값이 있는 경우가 많지만, API303의 원문 필드는 여전히 말 ID별 순위와 동일한 구조가 아니다.

API4_3 후보 92,695행의 말별 원문 필드 집계는 다음과 같다. `sjG3fOrd`는 양수 0행이다. 1C/2C 양수는 각각 84/825행이다. 400m 완주 5,535행은 3C/4C 값이 모두 0이다. 이 거리 영향과 원문이 실제로 비어 있거나 모순되는 사례를 구분한다.

## 결과 원문 이상 행과 취소 처리

2026-09-17~19 후보는 22경주 206행이며 204행은 `finish_time_seconds>0`이다. 나머지 2행은 2026-09-19 제주 4R 마번 2 `세계자랑`(`ord=94`)과 마번 5 `은하왕자`(`ord=95`)다. 공식 [KRA 심판 처분사항](https://race.kra.co.kr/referee/DecisionItem.do?Act=06&Sub=8&meet=2)에서 각각 출전제외와 출전취소로 확인됐다. 이 둘은 결과 시간·착순이 있는 완주마로 취급하지 않는다.

API4_3의 기존 정규화 열 `finish_status_raw`는 원문 `ord` 값을 복사한 열 이름일 뿐 상태 설명이 아니다. 일반 순위 외 코드에 임의로 출전제외·취소 등의 의미를 붙이지 않는다. 위 두 행의 상태는 별도 공식 심판 기록 근거로 확인된 내용이다. 또 2010-02-27 제주 6R 10행은 API4_3 원문에 `rank`와 `rcDist` key 자체가 없지만 완주시간은 양수다. 정규화 열은 각각 빈 문자열과 NULL로 나타난다. 누락된 거리나 등급을 보정하지 않았다.

## 파일과 재현 명령

- 추가 스키마 및 후보·coverage 뷰: `jeju/data/schema/migrations/20260930_add_api303_corner_rank.sql`
- 신규 core 생성용 스키마에도 같은 additive 객체 정의: `jeju/data/schema/jeju_native_core.sql`
- 기존 보존 응답 적재기: `jeju/scripts/load_api303_corner_rank_archive.py`
- 기계 판독 가능한 페이지·필드 구조·교차 집계: `jeju/research/20260929_api_detail_sources/api303_corner_rank_ingest_report.json`

```sh
python3 jeju/scripts/load_api303_corner_rank_archive.py
```

실행은 기존 manifest의 원문 페이지 SHA-256을 확인한 뒤 SQLite에 추가한다. 같은 attempt ID로 재실행하면 저장된 전체 payload와 정규화 행을 원문과 대조하고 중복 삽입 없이 종료한다. 마지막 적재 후 `PRAGMA integrity_check`는 `ok`, `foreign_key_check` 위반은 0건이다.
