# 고정 기준 DB 삭제·복구 가능성 및 10월 17일 구간 공백 검토

후속 사용자 승인으로 수행한 실제 적재·거리 정정은 [10월 17일 반영 보고서](../20261018_oct17_section_load/README.md)를 따른다. 아래와 기존 검토 원장의 읽기 전용·미적재 표시는 이 앞선 조사 시점의 상태다. 고정 기준 원본 소실과 새로운 구간 적재는 별개다.

검토일: **2026-10-18 KST**. 이번 작업은 조사·공식 원문 대조이며, 현재 DB·원본 백업·기존 기준 manifest를 변경하거나 복원하지 않았다.

## 1. 고정 기준 DB가 없는 이유

`jeju/research/20261017_core_refresh/baseline/jeju_native_core.sqlite3`는 **2026-10-17 19:16:12~19:16:39 KST 저장공간 정리에서 삭제**됐다. 삭제 원장에는 정확한 경로, 크기 1,912,885,248바이트, inode 98979541, SHA-256 `1de4756d4cb8824706d803097fc5b99c93c4324524fcef0a6db77bcc4fa87035`, 삭제 후 부재가 기록돼 있다. 기준 pair manifest의 기대 SHA와 일치한다.

- [삭제 실행 원장](../../../reports/storage_review_20261017/db_copy_deletion_receipt.json)
- [제주 정리 포인터](../../maintenance/db_copy_cleanup_20261017.json)
- `jeju/refresh/run.py`의 정기 갱신 정리는 자체 생성 롤링 백업만 대상으로 하며, 이 고정 기준 DB의 삭제 원인은 위 별도 저장공간 정리 원장으로 확인했다.
- 원장만으로 삭제 명령 자체나 누가 지시했는지는 특정하지 않았다.

## 2. 복구 가능성

| 대상 | 확인 결과 | 사용할 수 있는 의미 |
|---|---|---|
| 삭제된 고정 기준 DB와 같은 바이트·SHA의 사본 | 검사 가능한 프로젝트·마운트 경로 등에서 미발견 | 현재 확보한 사본으로 원본 그대로 복구됐다고 할 수 없음 |
| 최근 갱신 직전 롤링 백업 | SHA 일치, SQLite quick_check `ok` | 10월 17일 22시 갱신 전 상태로 복구할 수 있는 정상 백업 |
| `before_older_completion.sqlite3` | 기준 manifest와 35개 중 15개 테이블 행 수가 다름 | 기승자 분류만 되돌려 고정 원본을 재현할 수 없음 |
| 휴지통·홈의 일부 보호 경로 | macOS 접근 제한 | 미확인. 휴지통에 원본이 없다고 단정하지 않음 |
| Time Machine | 조회 결과 로컬 스냅샷·설정된 백업 대상 없음 | 이번 환경에서 해당 경로를 통한 복구 원본 미확보 |
| Git | `*.sqlite3` 무시, 해당 파일 추적 이력 없음 | Git 파일 복원으로 회수할 수 없음 |

**정상 롤링 백업:** `jeju/research/20261017_core_refresh/rolling_backups/20261017T220226_4747d5bd/jeju_native_core.sqlite3`.

- 크기 1,980,116,992바이트.
- SHA-256 `3382a2ed783493b18741482409b1d2c3229af23320b056568e1fe08a3a4fc79d`를 root가 별도로 재검산했다.
- 직전 기승자 종류 보완 186,428행을 포함한 전체 종류별 건수가 적용 원장과 일치한다.
- 이 백업은 삭제된 고정 기준보다 **나중 시점**이다. 기존 기준 경로에 복사한 뒤 옛 manifest를 유지하는 방식은 원본 복구가 아니며 기준 혼동을 만든다.

현재 사용 중인 `jeju/data/jeju_native_core.sqlite3`도 quick_check가 `ok`이고 SHA `e8ae5f9b2447f75d9847e76d34eb35cbf77d95e85e4e2f86bed91df12df5ae9f`가 최신 refresh manifest와 일치한다. 이번 사건은 현행 DB 소실과 구분한다.

**결론:** 현행 DB의 최근 백업 복구 경로는 정상이다. 삭제된 옛 고정 기준 DB와 동일한 원본 복구는 현재 확보된 파일로는 확인하지 못했다. 보호된 휴지통을 사용자가 확인하거나 별도 외부 백업에서 같은 원본을 확보할 가능성은 남는다. 새 기준이 필요하면 새 시점·새 manifest로 별도 버전을 정의해야 하며, 옛 기준을 복구했다고 표시하지 않는다. 논리적 재구성은 추가 적재·기존값 변경의 역전 검증이 필요하고 이번에 실행하지 않았다.

## 3. 10월 17일 제주 구간상세·통과조

공식 홈페이지 **1~7경주 모두 자료가 게시**돼 있다. 69두의 말 ID를 각 행의 공식 말 링크에서 직접 읽고 마번·착순을 DB와 독립 대조해 모두 일치했다.

- 말별 구간기록·통과순위: 69행 확인.
- 경주 전체 펄롱타임·통과거리·누적 통과타임: 39지점 확인.
- 통과조: 값이 있는 29지점 확인. 괄호·동일군 내부를 개별 착순으로 바꾸지 않았다.
- 7경주 모두 펄롱타임 합이 누적 통과타임 및 우승마 완주시간과 일치했다. 이는 내부 합산 검산이며 모든 측정값의 물리적 정확성 확정을 뜻하지 않는다.

어젯밤 **10월 17일 22:02 KST** 조회에서는 API6·API303이 각각 0행이었지만, **10월 18일 04:02 KST 재조회에서는 각각 7행**으로 응답했다. 동일한 요청 날짜·경마장·경주 집합을 확인했다. 따라서 API 제공 공백은 재조회 시점에 해소됐다. 정확히 언제 데이터가 게시됐는지나 원래 0행이었던 내부 원인은 확인하지 못했다.
