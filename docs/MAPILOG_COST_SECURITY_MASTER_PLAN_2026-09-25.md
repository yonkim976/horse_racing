# Mapilog 비용·보안 조사 종합 및 운영 개선 계획

최초 작성일: 2026-09-25 KST  
추가 점검 및 로컬 구현 기록: 2026-09-28 KST
메인 브랜치 통합 기록: 2026-10-08 KST

이 문서는 9월 23~25일 조사와 이후 대화에서 정리한 방향을 통합한 기준 문서다. **운영에서 확인한 사실, 로컬에 구현한 보호 기능, 앞으로 구현할 계획을 구분한다.** 최초 작성 때 코드·DB·클라우드 설정 변경, 커밋, 배포, 재공개는 하지 않았다. 9월 28일 로컬 구현 내용은 아래에 별도 기록했다. 운영 수치와 요금은 각 확인 시점 기준이며 실시간 상태를 뜻하지 않는다.

## 1. 운영 방향

**웹과 DB의 요청당 비용을 줄이고, 알려진 수집 봇을 차단하며, 대용량 기능은 서버 인증과 사용량 제한으로 보호한다.** 공개 사이트의 모든 봇을 완벽히 식별·차단한다는 보장은 하지 않는다. 식별하지 못한 봇이 공개 정보를 읽더라도 비용과 처리량을 제한하는 것이 목표다.

| 항목 | 정리된 방향 | 상태 |
|---|---|---|
| 기본 이용 | 일정과 기본 예측 결과는 로그인 없이 제공 | 목표 공개 범위 |
| 공개 데이터 처리 | 작은 사전 생성 결과·공통 캐시 사용, 방문마다 전체 DB 조회·모델 실행 금지 | 날짜 캐시·월별 달력 로컬 구현, 사전 생성은 후속 |
| 대용량 이용 | 상세 분석·과거 이력·기간 조회·CSV는 로그인 후 제한적으로 제공 | 인증 및 기능 경계 설계 필요 |
| 봇 대응 | Claude·불필요한 SEO 수집 봇 차단, 경로·IP·계정별 제한 병행 | Serpstat·Ahrefs 로컬 차단 추가, 계정별 제한 후속 |
| 용량 목표 | 기본 일정·예측을 이용하는 동시 사용자 100명 | 부하 검증 전 목표치 |
| 외부 보호 | 자체 최적화와 검증을 먼저 수행하고 Cloud Armor 도입 판단 | 이번 단계에서 도입하지 않음 |
| 운영 공개 | 재공개 조건을 충족할 때까지 기존 중단 상태 유지 | 마지막 운영 조회에서 비공개 확인 |

여기서 기본 예측은 승인된 모델의 저장·발행 결과를 뜻한다. 보안 작업을 이유로 예측 모델을 변경하거나 자동으로 새 모델을 승격하지 않는다. 화면·메뉴의 이름과 UX 개편은 별도 작업에서 정한다.

이는 공개 웹 접근 중단이다. DB·이미지·로그 등의 고정/보관 비용, 이미 발생한 사용량의 지연 반영까지 없애는 조치는 아니다. 중단 이후 앱 요청 로그가 없다는 것은 플랫폼에서 거절된 외부 시도까지 없었다는 의미도 아니다.

### 로컬 구현과 운영 적용의 구분

GPT-6 Luna / high 서브에이전트의 구현과 주 에이전트 검토로 프록시 신뢰, 캐시·메모리 상한, 경로별 제한, 응답·동시성 제한, XSS 방어를 로컬에 반영했다. 이후 진단 로그가 추가된 코드를 독립 재검증했다. **이 강화 코드가 운영에 배포됐다는 확인은 없으며, 본 작업에서도 배포하지 않았다.**

기존 구현 문서의 137개 통과는 앞선 검증 시점의 기록이다. 진단 로그 추가 후 당시 재실행한 웹·보안 테스트는 **Python 141개, Node XSS 2개 통과**, Ruff 및 `git diff --check` 통과였다. 기존 Starlette/httpx 경고 1건은 남았다. 9/25 최초 종합 문서 작성 때 테스트를 다시 실행한 것은 아니다. 9/28 변경 검증은 아래에 별도 기록했다.

이 결과는 운영 프록시·실제 DB·100명 사용 부하를 검증한 결과가 아니다. 기존 다중 페이지 회귀 테스트 일부는 시간 경과를 모의하므로 정상 사용자 오탐이 없다는 증거로 사용하지 않는다.

## 3. 비용 증가 원인

비용은 두 구간에서 각각 발생한다.

```text
Supabase ── 조회 결과 ──▶ Cloud Run ── HTML·API·파일 ──▶ 사용자 또는 봇
          DB egress                     웹 응답 egress
```

HTML gzip·응답 크기 상한은 이미 DB에서 받아온 데이터의 전송 비용을 되돌리지 못한다. CSS·JS만 CDN에 올려도 동적 HTML의 반복 DB 조회는 남는다.

### Supabase: 반복되는 전체 날짜 조회

9/23 약 22:24~22:29 KST 대시보드 확인값:

- `horse-racing-prod` 프로젝트 egress **62.269GB**.
- 조직 전체 **62.273 / 250GB**, 당시 egress 초과량 **0GB**. 기본 요금 전체가 0이라는 뜻은 아니다.
- 사용량이 큰 9/19·9/20의 차트는 **Shared Pooler Egress 100%**로 표시됐다.
- 앱은 브라우저에서 Supabase에 직접 접근하지 않고 서버에서 PostgreSQL을 조회한다.

9/18 16:24:57 UTC 이후 남아 있는 `pg_stat_statements` 통계:

| 메인 화면 쿼리 | 실행 횟수 | 누적 반환 행 |
|---|---:|---:|
| 전체 경주 날짜·상태 | 155,358 | 563,481,738 |
| 전체 경주 날짜 | 155,359 | 561,001,349 |
| 전체 주행심사 날짜 | 155,359 | 435,937,354 |
| 합계 | 466,076 | **1,560,420,441** |

메인 화면 로딩마다 위 세 조회에서 평균 합계 약 10,044행을 받고 선택 날짜의 경주·출전마·이력을 추가 조회한다. 최근 성적도 과거 기록을 받아온 후 Python에서 말당 5개만 남긴다. 반환 행 수는 반복 반환을 누적한 값이며 고유 데이터 수나 실제 네트워크 바이트가 아니다.

메인 페이지 성공 요청 표본에서 Claude 계열 UA 비중은 9/19 표본 2,000건 중 97.35%, 9/21~23 표본 10,000건 중 97.65%였다. 후자의 서로 다른 조회 날짜는 3,718개였다. **봇의 과거 날짜 순회와 반복 조회 구조가 결합한 것이 주원인이라는 근거가 강하지만, 62.269GB 전부의 원인을 봇으로 확정하거나 봇별 DB 바이트 비율을 계산할 수는 없다.**

당시 public 테이블 34개 모두 RLS 활성, `anon`·`authenticated`·`PUBLIC`의 직접 테이블 권한은 조회되지 않았다. 확인 범위에서는 DB 직접 노출보다 웹서버의 반복 조회라는 설명이 강하다. 함수·뷰·자격 증명까지 포함한 침해사고 전수 조사는 아니다.

### Cloud Run: Claude 외에도 큰 페이지 수집

9/1~9/25 12:19 UTC를 조회해 비-Claude 요청 **10,237건 전체**를 확보했다. 실제 자료는 9/19 02:58~9/23 18:41 KST에 있었으며 조회 상한으로 잘리지 않았다. 로그 보관은 30일이고 별도 싱크 제외 설정은 없었다.

비-Claude `responseSize` 합계는 **약 1.517GB**다. 정상 사용자·운영 테스트도 포함하며, 청구액이나 Supabase egress로 직접 환산하지 않는다.

| 자기신고 UA | 요청 | HTTP 로그 응답량 |
|---|---:|---:|
| Serpstatbot | 1,327 | 641.6MB |
| Applebot | 592 | 61.3MB |
| Googlebot 계열 | 263 | 28.4MB |
| GoogleOther | 149 | 23.8MB |
| AhrefsBot | 201 | 19.1MB |
| Yeti | 50 | 9.6MB |

OAI-SearchBot·bingbot·공유 미리보기 등도 확인됐다. UA만으로 업체의 공식 봇 신원을 인증한 것은 아니다.

Serpstat UA는 약 3시간 6분 동안 경주 상세 631건 등을 순회해 비-Claude 응답량의 약 42.3%를 차지했다. 최대 응답은 **1,512,908 bytes**, 전체 시간 평균 요청은 약 **7.1회/분**이다. 평균이 개별 순간 최대 속도를 나타내지는 않지만, 느린 지속 수집도 비용을 누적할 수 있음을 보여준다.

비-Claude CSV 기록은 POST 1건·405 응답뿐이다. CSV 보호는 예방 조치로 필요하지만 이번 확인 범위의 대량 전송 원인으로 단정하지 않는다.

## 4. 보안 탐색과 오류 조사

| 경로 탐색 | 관측 수 | 결과 |
|---|---:|---|
| `.env` 변형·`.git` | 1,217 | 해당 경로 HTTP 200 없음 |
| WordPress·`xmlrpc.php` | 839 | 해당 경로 HTTP 200 없음 |
| PHP 경로 | 905 | 해당 경로 HTTP 200 없음 |
| 경로 순회 인코딩 | 6 | HTTP 200 없음 |

범주는 중복될 수 있다. Chrome처럼 보이는 UA로 수백 개의 경로를 탐색한 사례도 확인되어 브라우저 UA를 정상 사용자 증거로 사용할 수 없다. 일부 요청은 운영자 테스트와 구별할 수 없다.

루트 `/`에 WordPress `rest_route` 쿼리를 붙인 2건은 200이었다. 라우트와 약 448~450KB의 응답 크기로 보면 홈 화면 반환일 가능성이 높지만 본문 로그가 없어 내용은 미확인이다. 파일·사용자 목록 탈취 성공으로 판정하지 않았다. **이번 로그에서 침해 성공 근거를 찾지 못했다는 것과 모든 침해 가능성을 배제했다는 것은 다르다.**

비-Claude HTTP 500 11건은 초기 리비전의 `/forecast` GROUP BY 오류 7건과 거리 통계의 `substr(date,...)` 오류 4건이었다. 현재 로컬 코드에는 해당 호환성 문제가 보완된 형태가 확인됐다. 별도 SSL EOF 오류 흔적도 있었으며 공격 성공을 뜻하는 증거는 아니다.

## 5. 로컬 방어 기능과 남은 문제

| 항목 | 로컬 구현 상태 | 추가 확인 사항 |
|---|---|---|
| 프록시 IP | 명시된 신뢰 프록시에서만 XFF 처리, 기본 신뢰 없음 | 실제 Cloud Run peer/XFF 전달 미검증 |
| 일반 요청 | 사용자 60회/10초·180회/분, 크롤러 10회/10초·30회/분 | IP 공유와 봇 UA 위장 고려 |
| 비싼 경로 | 공통 8회/10초·24회/분과 경로별 제한 | 빠른 탐색·공용 와이파이 오탐 가능 |
| CSV | 2회/10초·6회/분 | 로그인 및 계정별 한도는 미구현 |
| 응답 상한 | 압축 전 2MiB | DB 조회 비용까지 제한하지 못함 |
| 동시 처리 | 프로세스당 16개, 초과 503·Retry-After | 사용자 16명 제한이 아니며 100명 성능도 미검증 |
| 응답 캐시 | 128개·총 4MiB·항목당 512KiB·TTL 20초 | 날짜가 다르면 별도 캐시, 큰 응답은 캐시 불가 |
| 데이터 객체 캐시 | 128개·추정 8MiB·항목당 1MiB | 전체 날짜 목록 전용 공통 캐시는 별도 필요 |
| 날짜 메타데이터 캐시 | 9/28 로컬 추가: 프로세스별 최대 4MiB·TTL 300초 | 실제 DB 크기·정정 반영·인스턴스별 미스 검증 필요 |
| IP·정책 기록 | 각각 최대 4,096·8,192개 | 프로세스별 제한, 재시작·다중 인스턴스 고려 |
| XSS 방어 | 안전한 DOM 생성·이스케이프·숫자 검증 | 운영 악용 확인이 아닌 코드 예방 수정 |
| 진단 로그 | 경로 정규화, 정상 응답 1% 표본, 9/28 로컬에서 동일 사유 차단 로그 1분당 1건 | Cloud Run 기본 요청 로그와 전체 건수 감시 별도 필요 |

기존 로컬 시나리오에서 PC·모바일 19개 요청은 정상 통과했지만, 분석 페이지를 1초 간격으로 바꾸면 9번째에 429가 발생했다. 같은 IP의 4명이 분석을 각 2회 조회해도 공통 8회 한도를 소진한다.

제안됐던 **12회/10초·36회/분은 확정값이 아니다.** 공통 한도만 높여도 `analysis` 등 개별 한도가 8회·24회로 남으면 같은 경로의 오탐은 해결되지 않는다. 실제 사용자 시나리오로 공통·경로별 한도를 함께 조정해야 한다.

커스텀 진단 로그가 원본 IP·전체 쿼리·UA를 제외하더라도 Cloud Run 기본 요청 로그까지 같은 설정이라는 뜻은 아니다. 로컬의 모든 보호 기능이 월 청구액 상한을 보장하지도 않는다.

### 9/28 로컬 구현 추가 기록

- 홈 화면의 전체 경주·주행심사 날짜 및 상태 조회를 별도 공통 인덱스로 모아 프로세스별 최대 4MiB·TTL 300초로 캐시한다. 같은 프로세스의 서로 다른 날짜 요청이 캐시 미스를 합쳐 해당 조회를 공유한다. 데이터 동기화 이벤트에 의한 즉시 무효화와 여러 인스턴스 간 공유는 아직 없다.
- 홈 HTML에는 선택한 달의 날짜만 넣는다. 다른 달은 `/api/calendar?month=YYYY-MM`에서 받아오며, 이 경로에도 입력 검증과 사용량 제한을 적용한다. 과거 월 접근은 유지한다.
- 홈의 최근 경주 성적과 주행심사 성적은 SQL의 말별 순위로 유효한 최근 5행만 전송한다. 화면 표시 순서·심사 제외 코드 회귀 검사를 추가했다. 실제 운영 DB의 실행계획·전송량 감소 수치는 아직 측정하지 않았다.
- SerpstatBot·AhrefsBot UA와 관측된 WordPress `rest_route` 루트 탐색을 DB 접근 전에 거부한다. `robots.txt`에도 두 봇을 안내한다. UA 정책은 신원 검증이나 위장 봇 차단을 보장하지 않는다. 앱의 동일 차단 사유 진단 로그는 프로세스당 1분에 한 건으로 제한하고 다음 출력에 생략 건수를 포함한다. Cloud Run 기본 요청 로그에는 적용되지 않는다.
- 9/28 당시 이 변경은 별도 로컬 worktree에만 있었다. 당시 관련 Python 테스트 87개, JS 구문 검사, Ruff 및 `git diff --check`가 통과했다. 기존 Starlette/httpx 경고 1건은 남는다.

### 10/8 메인 브랜치 통합

메인의 최신 웹 화면과 origin token 보호를 유지한 채 위 변경을 메인 브랜치 코드에 이식했다. 메인 기준 웹·보안 테스트 68개가 통과했고 JS 구문 검사와 변경 파일 검사를 완료했다. 이 통합은 로컬 Git 작업이며 운영 배포나 재공개를 뜻하지 않는다. 운영 DB의 실행계획·전송량, 실제 프록시 환경, 동시 사용자 100명 부하는 별도 검증이 필요하다.

## 6. 목표 서비스 구조

| 이용 범위 | 제공 정보 | 원칙 |
|---|---|---|
| 비로그인 | 오늘·다가오는 일정, 기본 예측 요약 | 작게 사전 생성·캐시, 갱신 시에만 다시 생성 |
| 로그인 | 상세 분석, 과거 이력, 기간 조회 | 서버 인증 후 제한된 SQL 조회, 계정별 사용량 관리 |
| 다운로드 | CSV·대량 내보내기 | 별도 횟수·범위·동시 작업 제한 |
| 운영자 | 모델 실행·재학습·전체 데이터 추출 | 공개 요청과 분리 |

인증은 화면이나 버튼에만 붙이지 않는다. 기존 상세 URL, 모바일 경로, API, CSV에 직접 요청해도 서버가 인증·권한·한도를 먼저 검사해야 한다. 로그인 전 JS가 대용량 데이터를 미리 받아오면 안 된다.

현재 쿠키·Authorization 요청은 응답 캐시를 우회한다. 로그인만 추가하면 반복 DB 조회가 늘 수 있으므로 **공통 일정·예측 데이터 캐시와 사용자별 응답을 분리**해야 한다. 개인 데이터나 Set-Cookie 응답을 공용 캐시에 넣지 않는다. 로그인된 계정도 자동 수집에 사용될 수 있어 계정별 한도와 가입·로그인 시도 제한이 필요하다.

### DB·화면 최적화 작업

1. 전체 날짜·상태 데이터를 공통 캐시 또는 사전 생성 자료로 분리한다. 데이터 갱신 시 무효화, 캐시 용량, 동시 미스 합치기를 설계한다.
2. 달력은 필요한 월·주변 기간만 제공한다. 과거 조회 기능을 보존하면서 전체 기간을 매 응답에 싣지 않는다.
3. 최근 성적은 SQL에서 말당 필요한 5개만 반환한다. 정렬·실격 표시가 기존 결과와 같도록 검증하며 임의 기간 절단으로 이력을 누락시키지 않는다.
4. 큰 상세 HTML은 요약·페이지 분할로 줄인다. 분할한 API에도 같은 인증·사용량 제한을 적용한다.
5. 거의 변하지 않는 과거 결과는 길게 캐시하고 수정된 데이터만 갱신한다. 캐시 만료가 한꺼번에 DB 조회 폭주로 이어지지 않도록 한다.

1MB 응답을 50KB로 줄이면 본문 전송량은 약 95% 줄지만, 10만 회면 약 5GB가 된다(십진 단위 단순 예시, 실제 청구량 아님). 따라서 **크기 축소·DB 캐시·요청 제한을 함께 적용**한다.

## 7. 봇과 비정상 접근 정책

| 대상 | 권장 정책 | 유의점 |
|---|---|---|
| Claude 계열 | 기존 차단 유지 | UA 위장까지 막는 방식은 아님 |
| Serpstat·Ahrefs 등 불필요한 수집 봇 | robots.txt 및 앱의 조기 차단 정책에 포함 | 단시간 속도뿐 아니라 지속 수집량 고려 |
| GoogleOther 등 기타 수집 봇 | 서비스에 필요하지 않으면 차단 검토 | Googlebot과 같은 권한으로 묶지 않음 |
| Googlebot·Yeti·bingbot | 신원 검증 후 공개 요약과 별도 한도 | 이름만으로 허용하거나 무제한 면제하지 않음 |
| Applebot·공유 미리보기 | 검색·공유에 필요한 범위만 선택 허용 | 학습 사용 거부와 크롤링 차단은 구분 |
| 브라우저 UA·미식별 요청 | 공통 IP·경로 제한, 인증 기능은 계정 제한 | IP 하나가 여러 정상 사용자일 수 있음 |
| 비밀 파일·미사용 기술 경로 | DB 조회 전에 작은 거부 응답 | 정상 서비스 경로를 넓은 정규식으로 잘못 차단하지 않음 |

`robots.txt`는 자발적으로 준수하는 봇에 대한 안내다. UA 이름 차단도 보조 수단이다. 분산 IP와 브라우저 자동화에 대비한 공통 제한이 필요하며, 검색 봇에도 비공개 정보는 제공하지 않는다.

실제 프록시에서 사용자 IP가 올바르게 분리되는지 먼저 확인한다. 오탐을 해결하려고 모든 프록시를 신뢰하거나 조작 가능한 쿠키·UA를 사용자별 무제한 키로 사용하지 않는다. 한국 외 지역 차단은 정상 해외 사용자·검색 봇 영향 때문에 우선 보류한다.

앱 내부 차단은 Cloud Run에 요청이 도달한 후 작동하므로 거부 요청의 처리·응답·로그 비용이 일부 남는다. 차단 건수는 집계하되 상세 로그에는 표본 기록 또는 출력 상한을 둔다.

## 8. 동시 사용자 100명과 오탐 검증

100명은 기본 일정·예측을 이용하는 사용자 부하 목표이며 동시에 대용량 SQL 작업 100개를 실행한다는 의미가 아니다. 100명이 10초마다 한 번 탐색하면 평균 초당 약 10개 페이지 요청에 API·정적 파일 요청이 추가된다. 이는 설명용 예시로 실제 부하는 사용자 행동에 따라 달라진다.

Cloud Run 동시성은 사람 수가 아닌 동시 요청 수다. 현재 로컬 처리 슬롯 16개나 최대 인스턴스 3개만으로 100명 지원을 선언하지 않는다. 인스턴스별 메모리 제한을 합산해 정확한 전역 한도라고 간주하지도 않는다.

| 검증 시나리오 | 확인 지표·조건 |
|---|---|
| PC·모바일 기본 일정/예측 | 화면·API 성공, 응답시간, 전송량 |
| 100명의 지속적인 일반 탐색 | p95 응답시간, 5xx·429·503, CPU·메모리·DB 연결 |
| 동시에 처음 접속·캐시 미스 | 최초 응답 대기, 중복 SQL 실행, 갱신 중 처리 |
| 동일 와이파이 여러 사용자 | IP 공유로 정상 사용자 한도를 소진하는지 |
| 서로 다른 네트워크 | 실제 프록시 IP 해석과 별도 사용자 키 |
| 빠른 경주·필터 전환 | 필요한 정상 흐름이 429에 걸리는지 |
| 로그인 상세 조회·다운로드 혼합 | 기본 일정/예측이 무거운 작업 때문에 느려지는지 |
| 로그인 전 직접 URL·API 접근 | DB 대용량 조회 전에 거부되는지 |
| 요청 취소·시간 초과 | 처리 슬롯 반환, 무제한 대기·재시도 없음 |

먼저 보호된 환경에서 10→30→100명으로 단계적으로 검증한다. 처리 가능한 소수의 대용량 작업과 제한된 대기/재시도를 분리하고 무제한 대기열을 만들지 않는다. 실제 월 비용은 100명이라는 숫자만으로 산출하지 않고 요청 빈도·응답 크기·운영 시간·캐시 적중률로 계산한다.

429 비율만으로 오탐률을 판단하지 않는다. 봇 차단도 포함되므로 정상 사용자로 정해 둔 시나리오의 실패, 사용자 피드백, 경로별 집계를 함께 본다. 합격 기준인 응답시간·허용 실패율·월 예산의 구체 수치는 구현 전 확정해야 한다.

## 9. 외부 보호 경로와 Cloud Armor 비용

### 현재 권장 순서

자체 경량화·캐시·로그인·사용량 제한을 먼저 검증한다. 정상 사용자 100명 부하를 충족하고 비용이 안정적이면 당장 외부 보호를 도입하지 않고 운영 결과를 볼 수 있다. **거부 요청 자체가 계속 늘거나 분산 요청 때문에 정상 접속이 영향을 받는다면 외부 보호 도입을 앞당긴다.**

### 9/25 대화에서 확인한 요금 예시

글로벌 외부 로드밸런서, Cloud Armor Standard 보안 정책 1개·규칙 총 3개, 월 730시간 가정이다. 확정 견적이나 전체 서비스 월 비용은 아니다.

| 항목 | 예시 월 비용 |
|---|---:|
| 로드밸런서 전달 규칙 기본 비용 | 약 $18.25 |
| Armor 보안 정책 1개 | 약 $5 |
| Armor 규칙 3개 | 약 $3 |
| 고정 부분 합계 | **약 $26.25** |
| 글로벌 Armor 요청 처리 | **100만 요청당 $0.75** |

환율을 1달러=1,400원으로 가정하면 고정 부분은 약 36,750원이다. 실시간 환율을 확인한 수치가 아니다. 로드밸런서 데이터 처리·인터넷 전송·로그·선택한 CDN·세금 및 기존 Cloud Run·Supabase 비용은 별도이며 원화 청구 SKU도 확인해야 한다. 필요한 규칙 수가 늘면 예시와 달라진다.

Cloud Run에 Armor를 적용하려면 지원되는 외부 Application Load Balancer와 serverless NEG 등 앞단 구성이 필요하다. 도입 시 `run.app`과 기존 도메인 연결 등의 우회 경로를 함께 제한한다. 도메인 DNS만 바꿔서는 원본이 보호된다고 볼 수 없다. CDN 캐시 적중 요청과 원본 요청에 어느 보안 정책이 적용되는지도 별도로 확인한다.

외부 보호도 모든 봇 차단이나 정확한 청구액 상한을 보장하는 것은 아니다. 봇 판별·challenge 기능을 추가할 때는 해당 기능의 별도 요금도 확인한다.

## 10. 실행 순서와 완료 조건

아래는 **후속 구현 계획**이다. 9/28 현재 1·2단계 일부만 로컬 구현했고 나머지 완료 조건은 충족되지 않았다. 로컬 구현이나 이 문서 갱신은 운영 재공개 승인이 아니다.

| 단계 | 작업 | 완료 조건 |
|---|---|---|
| 1. 요청당 비용 축소 | 날짜 공통 캐시, 기간별 달력, SQL 최근 5개, 공개 화면·상세 HTML 경량화 | 같은 결과를 제공하면서 SQL 반환 행·응답 바이트가 감소 |
| 2. 자체 보호 보완 | 봇 정책 확장, 경로 조기 거부, 공통/개별 한도 정합성, 로그 출력 상한 | DB 전 차단, 캐시 우회·공용 IP 오탐 검증 |
| 3. 공개/로그인 분리 | 공개 일정·예측 캐시, 상세/API/CSV 서버 인증, 계정별 사용량·가입/로그인 제한 | 직접 API 접근 차단, 인증 캐시 혼합 없음 |
| 4. 실환경 검증 | 실제 프록시·DB·PC/모바일·공용 IP·100명 부하 | 합의한 성능·정상 사용자 성공 기준 충족 |
| 5. 비용 감시와 제한 공개 | 웹 응답·DB egress·캐시 미스·오류 감시, 기능 제한/비공개 전환 절차 | 감지·중단·복구 절차 검증 후 별도 재공개 판단 |
| 6. 필요 시 외부 보호 | 비용 견적, CDN/WAF, 원본 우회 차단 | 정상 접속과 캐시/보안 정책 적용 경로 검증 |

예산 알림·최대 인스턴스·앱 사용량 제한은 정확한 청구액 상한과 다르다. 비용 집계 지연, 고정비, 다른 서비스 비용을 고려한다. 급증 시 대용량 기능부터 제한하고 가능하면 기본 일정·예측을 유지하는 대응을 설계한다. 월 예산·일일 허용량·중단 임계값은 아직 확정하지 않았다.

재공개 전 게이트: 공개/로그인 경로 목록과 서버 인증을 확정하고, 실제 프록시 IP 구분·공용 IP 오탐·DB 쿼리 비용·10→30→100명 부하를 확인한다. 합격할 응답시간·정상 요청 실패율·일일 사용량과 중단 임계값을 운영자가 정한 뒤 검증 결과를 남긴다.

| `/analysis`, `/m/analysis`, `/races/{id}`, `/running-trials/{id}` | 상세 분석·경주·심사 이력 | 로그인 대상과 공개 요약 경로 확인 |
| `/validation`, `/racecourses/{course}/distances`, `/data-status` | 기간·통계·운영 상태 | 로그인 여부와 조회 범위 확인 |
| `/horses`, `/jockeys`, `/trainers`, `/owners` 및 상세 URL | 개체 목록·이력 | 공개 검색과 상세 이력 경계 확인 |
| `/api/analysis/export.csv` | 데이터 다운로드 | 로그인·계정별·기간별 한도 확정 |

- 공개 일정의 기간과 기본 예측 요약의 범위.
- 로그인 사용자에게 허용할 이력 기간, 조회·CSV의 분당/일일 한도.

- 100명 테스트의 사용자 행동, 응답시간·실패율 합격 기준.
- 월 운영 예산과 사용량 급증 시 기능 제한 임계값.
