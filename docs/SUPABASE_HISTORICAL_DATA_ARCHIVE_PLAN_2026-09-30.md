# 운영 DB 과거 데이터 보관·조회 계획

기준일: 2026-09-30 (KST)  
대상: Supabase `horse-racing-prod` (`xkykmhhkjtosptoibduo`)  
상태: **검토 문서. 보관 이전·DB 삭제·요금 설정 변경은 실행하지 않음.**

## 결론

오래된 원본을 Supabase Storage 또는 별도 객체 저장소에 보관하고 필요할 때 백엔드가 다시 읽는 방식은 가능하다. 그러나 Storage는 기존 PostgreSQL 테이블의 대체 조회 엔진이 아니다. 현재 웹앱과 분석 코드는 훈련·구간기록 등을 SQL로 직접 읽으므로, 파일만 업로드하고 DB 행을 제거하면 일부 과거 화면과 분석이 깨진다. **조회 경로 구현과 복원 검증이 먼저이고, 원본 DB 삭제는 맨 마지막 별도 결정**이다.

### 큰 테이블과 연도 분포

테이블 크기는 `pg_total_relation_size` 기준으로 데이터와 인덱스를 포함한다. 연도 비중은 **행 수**로 계산했으며, 해당 연도의 정확한 바이트 크기 또는 예상 절감액은 아니다.

| 테이블 | 전체 크기 | 전체 행 | 과거 구간 | 과거 행·비중 | 판단 |
| --- | ---: | ---: | --- | ---: | --- |
| `horse_training` | 약 1,792 MiB | 8,207,029 | 2024년 이전 | 7,023,715 · 85.6% | 1차 보관 후보 |
| `odds_snapshots` | 약 741 MiB | 5,640,975 | 2025년 이전 | 486,332 · 8.6% | 큰 테이블이지만 대부분 2025~2026년 자료. 우선순위 낮음 |
| `race_section_times` | 약 367 MiB | 1,823,443 | 2024년 이전 | 1,296,242 · 71.1% | 보관 여지는 있으나 경주 화면·모델 의존성 검증 후 판단 |
| `race_section_results` | 약 349 MiB | 연도별 실측 미실시 | — | — | 아직 보관량 산정 불가 |

`horse_training`의 2024년 이전 7,023,715행 중 6,887,558행은 조회 당시 `horses.is_active = false`, 136,157행은 `true`인 말에 연결되었다. 이는 **당시 운영 DB의 상태값**에 따른 구분일 뿐 공식 은퇴 확정이나 영구 보관 기준은 아니다. 보관 실행 시 현역 상태를 재검증하고, 재등록·상태 정정 시 필요한 이력을 DB로 되돌릴 수 있어야 한다.

## 권장 보관 경계

1. **운영 DB 유지:** 오늘·예정 경주, 예측 원장, 사용자 서빙에 필요한 결과·출전 정보, 현역마의 전체 출전 이력 및 예측 입력에 필요한 이력.
2. **우선 시험 후보:** 오래된 **비현역마 훈련 기록**의 작은 표본. 연도만으로 일괄 제거하지 않는다.
3. **후순위 검토:** 오래된 구간기록. 경주 상세 화면과 피처 생성의 직접 의존성이 있으므로 별도 조회·회귀 테스트가 필요하다.
4. **당분간 유지:** 최근 배당 스냅샷과 기본 경주·말·연결키 테이블. 배당 테이블은 행 대부분이 최근 2년에 집중돼 있어 단순 과거 절단의 절감 효과가 작다.
5. **연구 원본 별도 보존:** 로컬 분석 DB·기존 연구 산출물은 이 계획의 삭제 대상이 아니다. 모델 학습·재현이 운영 Supabase의 전체 SQL 이력에 의존하는지 먼저 확인한다.

## Storage로 옮긴 뒤 다시 읽는 방식

제안 흐름은 `화면 요청 → 백엔드 → 운영 DB 조회 → 보관된 범위이면 보관 색인 확인 → 비공개 객체 다운로드/캐시 → 필요한 행만 반환`이다. 브라우저가 비공개 보관 파일에 직접 접근하거나 서버 비밀키를 받아서는 안 된다.

- 압축 Parquet 등의 불변 파일을 **테이블·연도·경마장** 기준으로 나누고, 실제 말별·경주별 조회 패턴에 맞게 파일 크기와 색인을 시험한다. 연도 전체를 한 파일로 만들어 요청마다 통째로 다운로드하지 않는다.
- DB에는 최소한의 보관 색인(대상 범위, 객체 경로, 스키마 버전, 행 수, 체크섬, 생성 시각)을 남긴다. 정확한 색인 스키마는 조회 프로토타입 뒤 결정한다.
- 자주 보이는 목록·요약은 운영 DB에 유지하고, 오래된 원문 상세만 온디맨드로 읽는다. 다운로드와 파싱에는 SQL 조회보다 지연이 생길 수 있으므로 캐시와 실제 요청 기반 지연 측정이 필요하다.
- 파일은 비공개 버킷에 두고 백엔드만 접근한다. 같은 Supabase 프로젝트의 Storage만 단독 백업으로 삼지 않는다. 프로젝트를 삭제하면 그 프로젝트의 Storage 객체도 함께 사라지므로 독립된 보관 사본을 둔다.
- Storage 데이터 전송도 egress로 집계된다. 반복 다운로드가 DB 절감 효과를 상쇄하지 않는지 확인한다.

현재 직접 SQL 의존성 예시: `src/horse_racing/web/entities.py`의 말 훈련 이력, `src/horse_racing/services/section_read.py`의 구간기록, `src/horse_racing/web/race_page.py`의 배당, `src/horse_racing/analysis/features/base.py`의 훈련·구간 피처. 삭제 전에는 이 호출 경로를 모두 조사해야 한다.

## 추후 적용 순서와 중단 조건

1. 보관 범위와 웹 화면·배치·모델의 테이블별 의존성을 확정한다. 현역마 이력 및 원장·예측 입력 누락을 금지한다.
2. 삭제 없는 소규모 **복사 시험**을 한다. 동일 스키마·행 수·주요 키·해시를 기록한 파일과 별도 백업 사본을 만든다.
3. 백엔드의 보관 조회·캐시·오류 처리를 구현한다. 보관 저장소 장애 시 과거 상세만 제한되고 당일 경주·예측은 정상 제공되도록 분리한다.
4. 대표 말·경주·연도에 대해 DB 원본과 보관 조회 결과가 동일한지, 실제 화면 응답시간과 egress가 수용 가능한지 검증한다. 파일 재업로드가 아니라 **복원 재적재**도 시험한다.
5. 운영에서 일정 기간 이중 조회 또는 그림자 비교를 수행한다. 불일치·누락·과도한 지연이 있으면 원본 유지.
6. 위 조건이 모두 충족되고 별도 승인된 범위에서만 DB 행 정리를 계획한다. 외래키·참조 무결성·수집기 재적재 동작·롤백을 점검하고 작은 배치로 진행한다.
7. 정리 후 DB 크기, 실제 할당 디스크, 청구를 각각 다시 측정한다. 행 삭제만으로 **12 GB 할당 디스크가 자동 축소되지는 않는다**. 디스크 축소는 Supabase의 프로젝트 업그레이드/이전과 중단시간 계획을 별도로 검토한다. 프로젝트 컴퓨트 비용은 보관 파일로 옮겨도 없어지지 않는다.

**중단 조건:** 현역마 또는 모델 입력 누락, 웹 상세 불일치, 보관 파일 체크섬 불일치, 독립 사본 부재, 복원 실패, 예상보다 큰 조회 지연·egress, 비용 설정 변경 시 미승인 초과금 발생 가능성. 이 경우 DB 삭제를 진행하지 않는다.
