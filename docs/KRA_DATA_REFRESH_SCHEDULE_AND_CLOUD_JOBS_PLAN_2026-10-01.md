# KRA 운영 데이터 갱신 주기와 Google Cloud 예약 수집 계획

- 작성일: 2026-10-01
- 시간대: `Asia/Seoul` (KST)
- 현재 상태: **계획 문서화 및 첫 Supabase 수동 출마표 갱신·검증 완료. 클라우드 배포·예약은 미활성.** 최초 문서 작성과 후속 실행을 아래에서 구분한다.
- 목적: 데이터를 항목별 공개 주기에 맞춰 수집하고, 수동 검증을 거쳐 하나씩 자동화한다.

## 1. 기준과 확인 범위

사용자가 제공한 KRA 웹사이트 갱신 주기를 수집 일정의 기준으로 채택한다. 이는 **API 반영 시각이나 실시간 갱신 보장(SLA)이 아니다.** 안내 표가 모든 경마장에 동일하게 적용되는지는 미확정이며, 경마장별 API 관측으로 보완한다.

공개 예정 시각과 실제 API 관측 시각, DB 저장 시각을 구분한다. 예를 들어 오늘 호출에 성공했더라도 데이터 기준일이 어제이면 오늘 자료까지 갱신되었다고 표시하지 않는다.

이번 확인은 현재 저장소의 수집 코드·컨테이너 설정과 Fintor의 로컬 운영 문서, Google 공식 문서를 대상으로 했다. 실제 Google Cloud 예약 목록·최근 실행 성공 여부·결제 계정의 사용량은 조회하지 않았다.

## 2. 항목별 공개 기준과 권장 수집 시각

아래 수집 시각과 재확인 간격은 운영 제안이며, 아직 활성화되지 않았다. 공개 예정 시각 뒤 10분의 여유는 API 지연을 보장하는 수치가 아니라 초기 설정값이다.

### 표에 공개 시각이 없는 데이터

| 데이터 | 초기 운영 제안 | 주의점 |
|---|---|---|
| 출발훈련・수영훈련・언덕훈련 | 하루 1회, 최근 날짜 재조회 | 14:00 공개라고 단정하지 않음; 실제 관측 시각으로 조정 |
| 심판리포트 | 경주 후 저녁·다음 날, 최근 7일 보완 | 경주 결과와 동시 공개된다고 가정하지 않음 |
| 구간시간・통과착순・통과조 | 경주 후·다음 날 | 새 구간 원천 DB 갱신과 운영 반영을 별도 검증 |
| 주로빠르기 | 경주 후·다음 날 | 당일 경주 전 공개된 주로상태와 별개이며 초기 예측에 소급 사용하지 않음 |
| 확정배당 | 경주 후 저녁·다음 날 | 실시간 배당과 구분; 현재 계획은 실시간 배당 수집이 아님 |
| 위탁계약・현역/비현역 상태 | 기본정보 공개 후와 주간 대조 | 별도 데이터 공개 시각·API 연결 검증 필요 |

일요일 또는 금·토·일만 경마일로 고정하지 않는다. 연휴·월요일 경주를 포함한 실제 일정과 지역별 마지막 경주일을 사용한다. 영천 등 지역 확장 시 각 API의 지원 여부를 별도 확인한다.

## 3. 수집 완료와 최신성 판정

1. 응답 성공, 원문 보관, 정규화 성공, 기대 경주·출전마 범위 충족, 저장 후 조회를 단계별로 검증한다.
2. 빈 응답은 미공개·경주 없음·실제 자료 없음·원천 장애를 구분한다. 단순 HTTP 성공만으로 최신화 완료를 기록하지 않는다.
3. 공개 지연은 예를 들어 15~30분 간격으로 3회 재확인한 뒤 미완료로 남긴다. 이후 저녁·다음 날 보완하며 무한 재시도하지 않는다. 횟수는 API 허용량 측정 후 확정한다.
4. 최근 3~7일 겹침 수집으로 정정을 확인한다. 출전표는 해당 주 실제 경주 일정 전체를 포함한다.
5. 경주 전 공개된 관측값과 경주 후 결과에서 얻은 값의 출처·시점을 구분한다. 사후 보완값을 라이브 예측 입력으로 소급 해석하지 않는다.

추가 구현할 수집 실행 기록에는 다음을 남기는 것을 권장한다. 기존 테이블에 모두 존재한다고 가정하지 않는다.

- 실행 ID, 작업 종류, API/원천, 경마장, 조회 기간, 시작·종료 시각
- 원천 공개 시각(확인 가능할 때), 데이터 기준일, 최초 관측 시각, DB 저장 시각
- 원문 건수, 정규화 건수, 신규·변경 건수, 검증 결과
- `success`, `partial`, `not_published`, `failed`, `skipped` 등의 상태와 재확인 예정
- 비밀값을 제외한 오류 요약, 원문 위치·해시

## 4. 현재 코드에서 확인한 범위와 자동화 전 보완점

### 기존 명령은 역할이 다르다

- `src/horse_racing/cli.py`의 `sync_daily`: `schedule`은 일정·출전표·출발번호, `results`는 결과·구간·통과 관련 수집을 실행한다. 모든 운영 데이터를 갱신하는 명령이 아니다.
- `sync_latest`: 출전표, 결과, 기존 구간/통과 수집, 기수변경, 취소, 장구·폐출혈, 심판리포트, 체중, 조교, 진료, 출발훈련, 주행심사, 현역 말 프로필, 등급변동과 관계자 연결 복구를 실행한다. 이를 매 10분 전체 실행하지 않는다.
- 수영·언덕훈련과 조교사 소속 동기화는 별도 스크립트가 있으며 `sync_latest`에 포함되지 않는다.
- 출전등록말 API와 확정 출전표 API는 다른 자료다. 출전등록말·관계자 기본정보 등을 위 표에 적었다고 해서 현재 파이프라인에서 모두 자동 수집되는 것은 아니다.
- API77은 운영 레이팅 원천으로 사용하지 않는다. 경주별 레이팅은 출전표·경주 결과 기준이고, 말 목록 표시는 마지막 실제 경주 레이팅 기준을 유지한다.

### 당일 경량 작업

`scripts/sync_live_race_day.py`는 지정 날짜·경마장의 일정/결과, 기수변경, 체중, 취소를 수집한다. 취소를 마지막에 적용하며 확정배당·예측 발행은 생략한다.

자동화 전 다음을 검증/보완한다.

- 2026-10-01 수동 수집 준비 중 출전표 재적재가 기존 취소 플래그를 초기화하지 않도록 수정했고 회귀 테스트를 추가했다. 새 취소는 마지막에 적용하되, 재출전 승인·취소 철회는 별도의 공식 근거로 처리해야 한다. 병렬 작업 간 덮어쓰기는 추가 검증한다.
- 체중 수집은 `HorseWeightHistory`에 저장한다. 화면과 예측 입력이 이 최신 관측을 사용하는지 별도 확인한다.
- 기수변경 이력 저장과 실제 화면·모델 입력 반영을 각각 확인한다.
- 새로운 구간시간·통과착순·통과조의 권위 원천은 새 구간 DB다. 기존 API 수집만으로 해당 정규화 테이블 전체가 최신화된다고 간주하지 않는다. `scripts/import_score_point_sources.py` 등 원천 갱신·검증·운영 반영 경로를 연결한다.
- 자동 예측은 변경된 **채택 모델의 실제 입력**이 있을 때만 해당 경주를 대상으로 실행한다. 입상확률만 발행하고 초기 예측을 덮어쓰지 않는다. 결과 수집과 예측 발행의 성공 상태를 구분한다.

### 클라우드 실행 준비

- 현재 `Dockerfile`은 웹 전용 `web-prod` 의존성을 설치하고 `src`만 복사한다. 기본 실행은 Uvicorn이며 `scripts`가 포함되지 않는다. 이 이미지를 그대로 수집 작업에 연결할 수 있다고 가정하지 않는다.
- `cloudbuild.yaml`에는 웹 서비스 업데이트 단계가 있다. 수집 Job 배포를 위해 이 빌드를 그대로 실행하면 웹 배포까지 발생할 수 있으므로 별도 수집 빌드/배포 경로를 마련한다.
- 당일 스크립트는 실행 중 `gcloud secrets versions access`를 호출한다. 현재 이미지에는 `gcloud` 설치 단계가 없으므로, 클라우드에서는 Secret Manager의 비밀값을 런타임 환경으로 주입하는 방식으로 정리하는 것을 권장한다.
- 날짜 기본값이 시스템 로컬 시간에 의존하는 CLI가 있다. 클라우드 작업은 KST 날짜를 명시적으로 계산해 전달하도록 검증한다. Scheduler 시간대 설정만으로 Python의 시스템 시간이 바뀌지는 않는다.
- `scripts/launchd/`의 아침 09:00 출전표·저녁 22:30 결과 템플릿은 로컬 예약 자료다. 설치 여부·실행 성공은 이번에 확인하지 않았다. 클라우드 전환 전 기존 로컬/Codex 예약의 중복 실행 여부를 확인한다.

## 5. 권장 구조: Cloud Scheduler → Cloud Run Job

Google은 Cloud Scheduler에서 Cloud Run Job을 정기 실행하는 구성을 공식 지원한다. Scheduler는 실행 시각을 관리하고 Job이 Python 수집을 실행한 뒤 종료한다. 웹 서비스와 분리하므로 웹 공개 서비스를 재개하지 않아도 별도 수집 Job을 운영할 수 있다. [공식 실행 안내](https://docs.cloud.google.com/run/docs/execute/jobs-on-schedule)

권장 데이터 흐름:

`Cloud Scheduler → 수집 전용 Cloud Run Job → KRA API → 원문 보관·검증 → Supabase 저장`

역할은 다음과 같이 나눈다.

- Scheduler: KST 예약과 호출 권한 관리
- 수집 Job: 실제 날짜·경마장 판정, 필요한 API 수집, 검증, DB 반영 후 종료
- 웹 Cloud Run 서비스: 사용자의 조회·화면 응답만 담당
- 예측 작업: 필요한 모델 파일·의존성·입력 시점 검증 후 별도 연결

운영 설계 요구사항:

- 수집 전용 이미지와 서비스 계정을 사용한다. Scheduler 호출 계정에는 대상 Job 실행 권한을, 작업 계정에는 필요한 비밀값·원문 저장소 접근 권한만 부여한다.
- API 키와 DB 비밀값은 이미지·Git·로그에 넣지 않는다. Secret Manager에서 런타임으로 주입하며 환경변수 방식은 비밀 버전 고정을 검토한다. [Google 비밀값 관리 안내](https://docs.cloud.google.com/run/docs/configuring/services/secrets)
- Cloud Scheduler는 최소 한 번 전달 방식이므로 재호출을 예상한다. 동일 날짜·지역·자료의 재실행을 안전하게 만들고, 작업 간 중복 실행을 잠금/실행 기록으로 방지한다. Job의 task 수·parallelism을 1로 해도 서로 다른 execution이 겹치는 문제까지 해결되지는 않는다. [Scheduler 실행 보장](https://docs.cloud.google.com/scheduler/docs/overview)
- Scheduler의 호출 성공과 수집 Job의 최종 성공을 구분한다. 최종 실패·부분 실패·오래된 데이터·호출량 초과를 알림 대상으로 둔다.
- 원문 파일은 작업 종료 후에도 보존되는 저장소에 저장해야 한다. 컨테이너 안 파일만 남겨 원문 재현성을 잃지 않도록 한다.
- API 허용량은 서비스별 실제 승인량을 확인한다. 필요한 날짜·경마장만 호출하고 전 경마장·전체 과거 자료를 반복 조회하지 않는다.

### Supabase만 갱신하는 운영 전제

사용자의 후속 질문에 따라 **Supabase만 갱신한다는 가정**으로 우선 설계한다. 실제 DB 연결 설정을 변경했다는 의미는 아니다.

이 전제에서의 역할:

1. 클라우드 수집 Job은 Supabase만 갱신한다. 로컬 SQLite에 대한 이중 적재·동기화 작업은 운영 일정에서 제외한다.
2. 웹앱은 로컬 테스트와 향후 클라우드 서비스 모두 운영 데이터를 Supabase에서 읽도록 연결 대상을 검증한다. SQLite를 읽는 화면에는 Supabase의 변경이 나타나지 않는다. DB 저장 후에도 웹 캐시가 있다면 캐시 갱신 주기에 따른 지연은 별도로 관리한다.
3. 맥의 `data/horse_racing.sqlite3`는 별도 로컬 자료로 남으며 이후 최신성과 양쪽 DB 동일성을 보장하지 않는다. 필요한 경우에만 별도 내려받기/동기화를 진행한다.
4. 로컬 예측이 최신 당일 데이터를 사용하려면 Supabase에서 필요한 입력을 읽거나 검증된 입력 스냅샷을 내려받는 경로가 필요하다. 연구 DB나 기존 모델을 자동 변경하지 않으며, 현재 예측 경로가 이미 이를 수행한다고 가정하지 않는다.
5. Supabase에 저장만 하면 모델 재예측·프론트 갱신까지 자동 완료되는 것은 아니다. 수집 성공, 입력 변경 감지, 재예측 발행, 조회 캐시 반영을 분리해서 검증한다.

이 설계에서는 맥을 켜두지 않아도 클라우드 수집이 가능하다. 다만 예측을 로컬에서만 실행하는 동안에는 자동 예측을 위해 해당 로컬 실행 환경이 필요하다. 수집 자동화와 예측 자동화를 구분한다.

이 문서는 위 가정을 기록했으며 실제 DB 연결·동기화 방식은 변경하지 않는다.

## 7. 비용: Scheduler와 실행 비용을 구분

2026-10-01 확인한 공식 가격 기준, Scheduler는 호출 횟수가 아니라 **예약 작업 수**에 과금한다. 결제 계정별 월 3개 작업이 무료이고 초과 작업은 작업당 31일 기준 US$0.10이다. 일시중지 작업도 계산되며 무료 한도는 프로젝트별이 아니다. Fintor가 같은 결제 계정의 무료 한도를 사용 중이라면 경마 작업에도 과금될 수 있다. [Scheduler 가격](https://cloud.google.com/scheduler/pricing)

예를 들어 무료 슬롯이 남지 않았다면 추가 예약 1개는 Scheduler 부분만 약 US$0.10/31일이다. **이는 전체 운영 비용 견적이 아니다.** Cloud Run CPU·메모리·실행시간·최소 과금, 이미지 저장·빌드, 원문 저장, 네트워크, 로그, 비밀값 접근 및 DB 비용을 별도로 계산해야 한다. [Cloud Run 가격](https://cloud.google.com/run/pricing)

유료 리소스 생성 전에 경마장별 API 호출 수, 한 번 실행 시간, CPU/메모리, 주간 실행 횟수, 기존 무료 한도 사용량을 측정하고 예상 비용을 사용자에게 제시한다. 이번에는 비용 발생 리소스를 생성하지 않았다.
