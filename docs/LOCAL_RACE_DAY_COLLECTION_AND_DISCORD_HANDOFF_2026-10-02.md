# 경마 자동 수집과 디스코드 알림 운영 현황

작성일은 2026년 10월 2일이며 시간대는 Asia/Seoul이다. 주간 출마표와 매일 조교는 Google Cloud에서, 경주 당일 변경과 결과는 노트북에서 수집한다. 세 작업 모두 Supabase 운영 DB를 갱신한다. 로컬 SQLite 동기화, 모델 재예측, 웹 서비스 배포는 이 자동화에 포함하지 않는다.

이 문서는 현재 구현과 확인된 실행 결과를 정리한다. 이전 [전체 갱신 계획](KRA_DATA_REFRESH_SCHEDULE_AND_CLOUD_JOBS_PLAN_2026-10-01.md)의 최초 계획과 현재 적용 상태를 구분할 때 이 문서와 [클라우드 적용 기록](WEEKLY_CARD_CLOUD_CRON_SETUP_2026-10-01.md)을 함께 읽는다. 이 문서를 작성하면서 기존 수집 코드나 예약 설정을 변경하지 않았다.

## 적용된 세 가지 작업

| 작업 | 실행 위치 | 한국 시간 주기 | 범위 | 확인 상태 |
|---|---|---|---|---|
| 주간 출마표 | Google Cloud Run Job과 Cloud Scheduler | 수요일 17:10, 18:10, 19:10 | 동적 주간 일정, 확정 출전표, 출발번호, 장구 증감 | 수동 및 예약 경유 실행 검증 완료 |
| 매일 조교 | Google Cloud Run Job과 Cloud Scheduler | 매일 14:30 | 실행일 포함 최근 7일의 일반, 출발, 수영, 언덕조교 | 수동 및 예약 경유 실행 검증 완료 |
| 경주 당일 | macOS launchd와 Python | 약 2분 간격 | 오늘 개최 경마장 전체의 체중, 기수변경, 출전취소, 결과 상세 | 실제 자동 수집과 저장 및 알림 확인 |

2026년 10월 2일 17시대 읽기 전용 확인에서 `mapilog-weekly-entry-cards`와 `mapilog-daily-training` Scheduler는 모두 ENABLED였고 시간대와 예약은 위 표와 일치했다. Google 프로젝트는 `mapilog-509017`, 리전은 `asia-northeast1`이다. Supabase 대상은 `xkykmhhkjtosptoibduo`다. Fintor와 기존 웹 서비스를 변경하지 않았다.

주간 출마표는 이미 시작된 경주나 당일 변경을 덮어쓰는 작업이 아니다. 당일 작업은 사전에 DB에 저장된 오늘 출마표를 기준으로 하므로 오늘 출마표가 누락돼 있으면 이를 자동 생성하지 않는다. 연휴 경주는 요일이 아니라 저장된 일정으로 판단한다.

## 당일 수집 범위

한 경주만 수집하거나 다음 경주와 직전 경주만 선택하는 방식이 아니다. 오늘 개최되는 경마장마다 날짜 단위로 아래 API를 조회하고, 확인된 값을 기존 출전행에 반영한다.

| API | 조회 정보 | 운영 반영 |
|---|---|---|
| API25 출전마 체중 | 체중과 증감 | 체중 이력과 출전행의 체중 및 증감 |
| API10 기수변경 | 변경 전후 기수, 부담중량, 사유 | 변경 이력과 출전행의 기수 및 부담중량 |
| API9 출전취소 | 취소 대상과 사유 | 취소 이력과 출전행의 취소 상태 |
| API155 경주결과 | 착순과 기록 등 | 아직 결과가 없는 출전행의 결과 보완 |
| API156 경주결과 상세 | 상세 결과, 레이팅, 주로와 날씨 등 | 결과 정정과 제공된 경주 상세 값 |

API156에서 얻은 주로와 날씨는 그 원천에 실제로 제공된 값만 반영한다. 경주 직전 주로 상태를 독립 실시간 API로 수집하거나 당시 공개 시각을 확인한 것은 아니다. 이 값을 초기 예측 입력으로 소급 사용하지 않는다.

예를 들어 3경주가 끝나면 3경주의 새 결과를 반영하면서 이후 경주의 발표된 체중, 기수변경, 취소도 확인한다. 이미 끝난 경주의 공식 결과 정정도 확인한다. API155로 이미 저장된 결과를 되돌리지 않으며 API156을 상세 결과 정정 원천으로 사용한다.

## 수집 시간과 종료 기준

- 정상 일정은 오늘 전체 첫 경주 예정 시각 1시간 전부터 마지막 경주 예정 시각 2시간 후까지다.
- 해당 경마장의 모든 경주 결과가 갖춰지면 그 경마장의 API 재확인은 10분 간격으로 줄인다. 다른 경마장의 경주가 남아 있으면 그 경마장은 약 2분 간격을 유지한다.
- 예정 시각이 일부 누락되면 임시로 09:00 이상 21:00 미만 구간을 사용한다.
- 자동 실행에는 08:00 이상 22:00 미만의 추가 제한이 있다. 정상 일정 창도 이 제한을 넘어서 수집하지 않는다.
- 오늘 저장된 일정은 첫 경주 10:50, 마지막 경주 17:55이므로 API 수집 창은 09:50부터 19:55까지다. 자정까지 수집하는 설정이 아니다.
- 어제 결과의 다음 날 정정 보완은 이 worker에 구현돼 있지 않다. 별도 사후 보완 작업이 필요하다.

launchd 예약은 창 밖에도 남아 있지만 조건에 맞지 않으면 API 수집을 건너뛴다. 2분은 목표 조회 간격이며 엄격한 실행 시각이나 공식 발표 뒤 2분 내 반영을 보장하지 않는다. API 공개 지연, 네트워크, 노트북 상태, 작업 소요가 실제 지연에 영향을 준다.

## 중복 방지와 저장 안전성

- 수동 실행, launchd, 전경 watch는 동일한 로컬 파일 잠금과 전용 PostgreSQL advisory lock을 사용한다. 이 worker의 동시 실행을 막지만 모든 다른 수집기의 쓰기를 전역 차단하는 것은 아니다.
- 날짜, 경마장, 공식 말 ID, 경주번호, 제공되는 출전번호와 거리 등을 기존 출전표와 검증한다. 식별이 맞지 않으면 해당 단계는 실패로 남긴다.
- 같은 업무 키는 기존 행을 갱신한다. 체중, 기수변경, 취소, 결과를 매번 신규 행으로 추가하지 않는다.
- API25의 미발표 체중 0은 유효 측정치로 저장하지 않는다. 빈 응답이나 미발표 값으로 정상 체중과 기존 취소를 지우지 않는다.
- 기수변경이 여러 번이면 응답 순서가 아니라 변경 연결 관계로 최종 기수를 판정한다. 연결이 모호하면 자동 추정하지 않는다.
- 모든 비취소 출전마에 공식 착순 값이 있고 출전표 범위가 갖춰진 경우에만 완료로 표시한다. 이는 결과 범위 검증이며 별도 공식 확정 선언 시각을 확인한 뜻은 아니다.
- 각 API 단계는 독립적으로 저장한다. 일부 실패에도 성공한 다른 단계는 남을 수 있으므로 실행의 completed, partial, failed를 구분한다.

업무 데이터 중복과 원문 관측 이력은 다르다. 당일 worker는 실행 이력을 매번 남기되 로컬 상태에 저장된 응답 해시와 달라진 원문만 추가 보관한다. 상태 파일을 잃으면 동일 원문이 다시 보관될 수 있지만 업무 키 중복 방지는 유지된다. 원문은 로컬 `data/raw/kra` 계열에 보관하며 클라우드 작업의 GCS 원문 저장과 구분한다.

## 디스코드 전송 범위

기존 사용자 웹훅을 유지했다. 웹훅 주소와 토큰, DB 비밀번호, API 키는 문서에 기록하지 않는다. 로컬 비밀 설정과 클라우드 Secret Manager 참조 방식은 [기존 적용 기록](WEEKLY_CARD_CLOUD_CRON_SETUP_2026-10-01.md)에 있다.

당일 자동 수집 알림은 모든 응답을 전송하는 방식이 아니다.

| 상황 | 현재 알림 |
|---|---|
| 체중 또는 증감 변경 | 변경 건수와 말별 일부 상세 |
| 기수 또는 부담중량 변경 | 변경 건수와 변경 후 값 |
| 출전취소 상태 변경 | 취소 사실 |
| 착순 또는 완주기록 변경 | 변경 건수와 말별 일부 상세 |
| 새로 완료된 경주 | 경주 목록 |
| 수집 오류와 복구 | 오류 종류 요약과 복구 안내 |
| 같은 데이터를 재조회하고 변경 없음 | 자동 실행에서는 보내지 않음 |
| 사용자가 수동 실행 | 변경이 없어도 실행 요약 전송 |
| 주로, 날씨, 레이팅, 상금, 사유 문구만 변경 | 현재 별도 변경 알림 대상 아님 |

전체 변경 건수는 요약하지만 말별 상세는 최대 8건이고 메시지 길이에도 제한이 있다. 기수변경과 취소의 상세 사유는 DB에 저장되지만 현재 알림 본문에는 없다. 신규 사유만 수정돼도 별도 알림이 나오는 것은 아니다. 기수 상세에도 변경 전후 대조는 아직 표시하지 않는다.

동일 오류 알림은 30분 간격으로 제한한다. Discord 전송 실패가 성공한 DB 저장을 되돌리거나 다시 수집시키지 않는다. 전송이 모호한 경우 자동 재전송하지 않으므로 장애 시 알림 유실 가능성이 있다. 프로세스 시작 전 권한 차단, 노트북 종료나 잠자기 등은 프로그램에서 알림을 보낼 수 없으며 독립 감시 경보는 없다.

주간 출마표와 매일 조교의 알림 규칙은 별도다. 두 클라우드 작업은 실행 요약과 실패 알림을 보내며 당일 worker의 변경 없음 무알림 규칙을 그대로 적용하지 않는다.

## 속보와 미수집 항목

마체 이상이 출전취소 API의 사유로 제공되면 저장할 수 있다. 오늘 부경 2경주 6번 위즈덤픽의 사유 `왼 뒷다리 절음`이 API9 원문과 DB에 동일하게 저장된 것을 확인했다.

별도 속보 화면 전체는 수집하지 않는다. 취소되지 않은 말의 이상 공지, 출전제외와 취소의 구분, 출발 예정 시각 변경, 경주 전체 취소, 공지시각은 추가 원천 대조가 필요하다. [마사회 속보 화면](https://race.kra.co.kr/raceFastreport/ChulmapyoChange.do?Act=03&Sub=1&meet=1)의 모든 항목을 현재 worker가 반영한다고 간주하지 않는다.

확정배당, 실시간 변동 배당, 구간시간과 통과 관련 새 원천, 심판리포트, 진료, 관계자 기본정보, 예측 재실행은 당일 worker에 포함되지 않는다. API156에서 제공되는 결과 레이팅은 예외적으로 출전행에 반영한다.

기존 배당 API는 [확정배당 원천](https://www.data.go.kr/data/15058559/openapi.do)이다. 경주 전 변동 배당의 대체물로 사용하지 않는다. 배당 수집과 `확정배당 발표 대기` 화면 표기는 제안 상태이며 구현하지 않았다. 현재 레이팅 화면은 0과 null을 모두 `—`로 표시한다. 이를 전부 `추후 공지`로 바꾸지 않았고 미부여와 정보 없음 구분도 아직 제안 상태다. 말 목록은 마지막 실제 경주 레이팅 정책을 유지한다.

## 수동 실행과 예약 관리

수동 갱신은 오늘 KST 날짜에 대해서만 실행하며 자동 시간 창을 적용하지 않는다. 과거 날짜 백필 명령이 아니다.

```bash
bash /Users/kimyongjin/Desktop/horse_racing/scripts/run-live-race-day.sh
```

예약 상태 조회, 중지, 재등록은 다음과 같다. 중지는 이 노트북 당일 작업만 대상으로 하며 클라우드 예약을 변경하지 않는다. 예약 파일은 보존한다.

```bash
cd /Users/kimyongjin/Desktop/horse_racing
.venv/bin/python scripts/manage-local-race-day.py status
.venv/bin/python scripts/manage-local-race-day.py stop
.venv/bin/python scripts/manage-local-race-day.py install
```

수집 없이 계획만 확인하려면 다음을 사용한다.

```bash
.venv/bin/python -m horse_racing.jobs.local_race_day
```

예약 대신 전경 자동 실행을 쓰려면 기존 예약을 먼저 중지한다. 두 방식을 동시에 상시 실행하지 않는다.

```bash
caffeinate -i .venv/bin/python -m horse_racing.jobs.local_race_day --apply --watch
```

전경 실행은 터미널을 유지해야 한다. launchd 예약은 코덱스와 터미널을 닫아도 동작하지만 로그인, 인터넷, 잠자기 해제와 필요한 파일 접근 권한이 있어야 한다. 뚜껑을 닫거나 전원을 끈 상태에서 계속 수집한다고 보장하지 않는다. 과거 Python 데스크탑 접근 대기는 사용자의 허용 후 정상 실행으로 확인됐다. 권한을 우회하지 않았다.

수집에 AI 채팅이나 예측 모델 호출은 없다. 이 당일 작업에 새 Cloud Run과 Scheduler를 만들지 않았지만 기존 Supabase, 비밀값 접근, 저장과 네트워크 등의 비용이 모두 0이라는 뜻은 아니다. 클라우드 두 작업의 승인 당시 비용 가정은 [적용 기록](WEEKLY_CARD_CLOUD_CRON_SETUP_2026-10-01.md)을 참고한다. 실제 청구 총액이나 상한을 보장하지 않는다.

## 실행 근거와 운영 확인

- 구현 파일은 [당일 worker](../src/horse_racing/jobs/local_race_day.py), [반영 서비스](../src/horse_racing/services/live_race_day.py), [LaunchAgent](../scripts/launchd/com.horse-racing.live-race-day.plist), [관리 스크립트](../scripts/manage-local-race-day.py)다.
- 로그는 `data/logs/local-live-race-day.log`, 오류 로그는 `data/logs/local-live-race-day.err.log`다. launchctl의 not running은 다음 주기를 기다리는 정상 유휴 상태일 수 있다. 마지막 종료 코드와 실제 로그 및 DB 실행을 함께 확인한다.
- 상태와 API 요청 계수는 `data/state/local-race-day.json`에 있다. 기본 800회 제한은 endpoint별 오늘 이 노트북 수집기의 안전 한도이며 공공데이터포털의 계정 전체 허용량을 조회한 값이 아니다. 다른 작업의 호출도 계정 한도에 영향을 줄 수 있다.
- 당일 worker의 DB 실행은 `ingestion_runs.source=laptop/live-race-day/v1`이다. records_written은 단계별 변경 출전행 수의 합으로 실제 SQL 쓰기 수나 전체 주기의 고유 변경 말 수와 동일하지 않다.
- 초기 검증은 관련 테스트 104개 통과와 Ruff, 셸 문법 및 plist 검사 통과였다.
- 13:53 KST 확인에서 자동 실행 9회 오류 0건, 당일 체중 중복 키 그룹 0건이었다. 제주 5경주 체중 10두와 부경 3경주 결과 11두의 Discord 메시지는 새 메시지 전송 없이 실제 기존 메시지를 조회해 확인했다.
- 문서 작성 중 17:06 KST 로그 확인에서는 자동 수집 요약 103건, 기록된 오류 이벤트 0건이었다. 당시 최신 실행 20045의 수집 소요는 1.78초였다. 이는 그 확인 시점의 증거이며 이후 모든 실행 성공을 보장하지 않는다.
