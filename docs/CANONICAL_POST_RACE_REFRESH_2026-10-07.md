## 저장 원천과 시간 의미

- API215 `JudgeReport`: 심판위원, 심판 판정 원문, 추가 판정, 기수 변경 메모, 날씨를 `race_steward_reports`에 보존한다.
- API4_3 `raceResult_3`: 말별 구간시간과 개별 통과순위를 `race_section_times`에 저장한다.
- API303 `corner_rank`: 경주 전체의 공식 통과조 표기를 `race_passing_groups`에 저장한다.
- API6_1 `raceDetailSectionRecord_1`: API303 통과조와 경주 거리의 독립 대조에 사용했다. 경주 전체 펄롱 기록을 말별 기록으로 대신 넣지 않았다.
- 공식 `dacom11` 성적표: 말 이름·출전번호·완주순위·완주시간·출발 200m·종반 600m·종반 200m와 제공된 코너시간을 대조했다. 서울의 종반 600m·200m는 이 명시적 열에서 추가했다.

서울은 `se*AccTime`, 부산·영천은 `bu*AccTime`을 누적시간으로 저장한다. 제주 `jeG3fTime`·`jeG1fTime`은 종반시간으로 저장한다. 부산·영천의 종반·구간 필드는 기존 성적표 원천 계약대로 별도 시간 종류로 구분했다. 시간값이 크거나 작다는 이유로 시간 종류를 추정하지 않았다.

제주 G1F의 `position_raw`는 G1F 지점의 통과순위이며 종반 200m 소요시간의 순위가 아니다. 제주 G3F는 종반시간만 저장하고 개별 통과순위·통과조를 만들지 않는다. 서울에도 G3F 통과조를 새로 만들지 않았다.

영천 성적표는 공식 Text 목록의 부산 피드에서 제공된다. 다운로드 목록의 피드 번호를 운영 경마장으로 그대로 사용하지 않고, 성적표 본문의 `영천`과 API의 meet 4, 출전마 ID 및 경주 자연키를 확인했다.

기존 구형 `race_section_results`·`race_passing_summaries`에 이번 범위의 자료를 추가하지 않았다. 적재 후 10월 2~5일의 해당 구형 테이블 행 수는 각각 0이었다. 구형 테이블에 남아 있는 과거 데이터는 이번 작업에서 삭제하지 않았다.

이 32두는 말의 다른 구간기록까지 빠진 것이 아니다. API4_3의 해당 개별 순위 필드가 0이지만 API303과 API6_1에는 서로 일치하는 통과조가 있다. 통과조의 괄호 내부 표기를 정확한 개별 순위로 임의 변환하거나 시간순으로 순위를 만들어 넣지 않았다. 따라서 **시간·통과조 최신화 완료와 모든 지점의 개별 순위 완비는 다른 주장**이다.

10월 7일 추가 확인에서 공식 웹 성적표의 말별 순위에도 해당 열이 `-`로 표시됨을 확인했다. [제주 10월 2일 7경주](https://race.kra.co.kr/raceScore/ScoretableDetailList.do?Act=04&Sub=1&meet=2&realRcDate=20261002&realRcNo=7)는 1,400m이며 2C 시간·통과조가 S1F와 같지만 말별 2C 순위는 비어 있다. [부산 10월 2일 5경주](https://race.kra.co.kr/raceScore/ScoretableDetailList.do?Act=04&Sub=1&meet=3&realRcDate=20261002&realRcNo=5)는 1,300m로 G6F가 출발 후 100m 지점이다. 해당 누적시간·공식 통과조는 있어도 말별 G6F 순위는 `-`다. 부산 6경주 역시 API에서 같은 G6F 순위 미제공을 확인했다. 따라서 수집 과정의 누락은 아니다. 마사회가 왜 이 지점의 개별 순위를 생략하는지에 대한 내부 규정·정확한 이유는 확인하지 못했으므로, 중복 지점 등 추정을 공식 이유로 단정하지 않는다.

취소·제외는 서울 10월 4일 1경주 5번, 서울 10월 5일 5경주 4·8번, 제주 10월 3일 2경주 2번, 제주 10월 5일 3경주 7번, 부산 10월 2일 2경주 6번이다. API 착순 코드는 마지막 부산 건이 95, 나머지는 94였다. 빈 시간과 0값을 정상 기록으로 적재하지 않았다.

## 재현 가능한 추가 적재

기존 `race_point_source_batches`는 지역·연도별 하나의 파일만 허용해 이후 경주일 자료를 붙일 수 없었다. [마이그레이션](../supabase/migrations/20261007051806_allow_incremental_score_point_batches.sql)으로 `(meet_code, race_year)` 유일 제약을 일반 인덱스로 바꿨다. `source_file` 유일성, 원천 해시, 기존 FK와 업무 기본키는 유지했다. 원격 마이그레이션 버전과 저장된 파일명이 일치한다.

기존 연도별 원천 배치 31개는 유지하고, 신규 경마장·경주일별 JSON 원천 배치 8개를 추가했다. 기존 연도별 원천 DB를 수정하거나 과거 원천의 SHA-256·건수를 새 자료로 덮어쓰지 않았다. 기존 [연도별 적재기](../scripts/import_score_point_sources.py)의 배치 조회도 연도가 아니라 정확한 `source_file`을 기준으로 변경했다.

신규 실행기는 [canonical_post_race.py](../src/horse_racing/jobs/canonical_post_race.py)다. 먼저 API·Text를 네트워크에서 수집하고 자연키와 공식 기록을 대조한 뒤, 별도 적용 단계에서 SHA-256과 Supabase의 출전행·완주 결과를 재확인한다. 해당 경마장·경주일의 추가는 짧은 트랜잭션에서 수행한다. 오류가 나면 그 경마장·날짜의 추가를 롤백하며, 이전 날짜의 성공까지 되돌리지 않는다.

기존 값과 다른 원천은 자동 덮어쓰기하지 않고 중단한다. 정정 자료는 충돌 원인을 확인한 후 별도의 정정 절차가 필요하다. 같은 적용 파일 재실행은 기존 값과 원천 배치를 대조하고 새 업무 행을 추가하지 않는다. 새로운 수집 파일로 이미 채운 날짜를 다시 적재하는 일반적인 정정·겹침 기간 동기화는 이번 실행기의 지원 범위가 아니다.

수집 범위는 Supabase에 이미 존재하고 `completed`인 경주다. 출전표가 없는 경주를 자동 생성하거나 모델 예측을 실행하지 않는다. `--apply` 없이도 공식 API 호출과 로컬 원문 파일 저장은 발생하지만 DB 쓰기는 하지 않는다. 이후 실행은 아직 채우지 않은 완료 경주일로 범위를 지정한다.

```sh
cd /Users/kimyongjin/Desktop/horse_racing
.venv/bin/python -m horse_racing.jobs.canonical_post_race --start 2026-09-21 --end 2026-10-07

# 위 수집 결과의 manifest를 검토하고 그 정확한 경로로 적용한다.
.venv/bin/python -m horse_racing.jobs.canonical_post_race \
  --manifest data/research/score_point_updates_20261007_141625/manifest.json --apply
```

두 번째 명령은 이번 적용 자료로 중복 여부를 다시 확인하는 명령이다. DB 연결은 기존 Secret Manager 비밀값과 프로젝트 대상 검증을 사용하고 SQLite로 우회하지 않는다. 비밀번호·API 키·Discord 웹훅은 문서와 검증 자료에 기록하지 않는다.

## 검증과 보존 위치

공식 API 4종과 Text 8건을 검증한 원문 문서 40개를 Supabase `source_documents`에 연결했다. 실행 이력은 `ingestion_runs` 21464~21471이다. 원문 파일 자체는 로컬 연구 폴더에 있고, Supabase에는 출처·로컬 경로·해시를 저장했다. 이번에 GCS나 Storage로 원문을 업로드하지 않았다.

적재 후 별도 Supabase 조회로 67경주 모두 비어 있지 않은 심판리포트와 통과조, 694두 모두 구간기록을 확인했다. 출발 200m·종반 600m·종반 200m는 각각 694행, 새 구간시간의 null 시간은 0행이었다. 제공된 누적시간과 종반시간의 합산 불일치는 0쌍이었다. 같은 manifest 재실행으로 추가된 심판·구간·통과조는 모두 0행이었다.

서울·제주의 공식 Text 통과순위와 API4_3에서 함께 제공된 개별 순위 2,351쌍도 대조했으며 불일치는 0쌍이었다. 부산·영천에 이 2,351쌍 대조 결과를 확대 적용하지 않는다.

새 실행기와 기존 구간·통과조·DB·feature 비교 테스트 42개 및 Ruff가 통과했다. 관련 네 테이블의 RLS는 활성 상태로 유지했다. 보안 advisor도 변경 전후 모두 기존 `rls_enabled_no_policy` 정보 항목 47개로 같았으며 새 권한·정책을 열지 않았다. 해당 정보 항목의 의미는 [공식 안내](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)를 따른다.

이번 범위 밖의 과거 품질 이슈는 기존 판정을 유지한다. 예전 제주 기록의 시간 종류 검증이나 과거 누적·종반 충돌이 이번 갱신으로 모두 해결됐다는 뜻은 아니다.
