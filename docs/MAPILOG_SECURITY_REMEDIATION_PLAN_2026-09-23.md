# Mapilog 보안·비용 방어 수정 계획 및 실행 기록

작성일: 2026-09-23. 이전 사고 근거는 [비용·보안 점검 보고서](MAPILOG_COST_SECURITY_AUDIT_2026-09-23.md)를 참조한다.

## 목표와 작업 범위

외부 접속 중단 상태를 유지하면서, 공개 웹 요청으로 발생할 수 있는 제한 우회·메모리 증가·과도한 조회/응답·HTML 삽입 문제를 수정한다. 이번 사용자 승인 범위는 아래 1·2단계의 로컬 구현과 검증이다. 로그인, CDN/WAF 구축, 클라우드 권한 변경, 운영 재배포·재공개는 후속 단계로 남긴다.

기존 작업 트리에 기능·연구·DB 변경이 섞여 있으므로 초기화하거나 일괄 커밋하지 않는다. DB 마이그레이션이나 운영 데이터는 변경하지 않는다.

## 확인된 문제

| 우선순위 | 확인 내용 | 재현/근거 | 수정 방향 |
|---|---|---|---|
| 높음 | X-Forwarded-For 첫 값을 신뢰 | 로컬 헤더 변조 20회가 제한을 우회 | 신뢰 프록시를 명시하고 검증된 체인만 사용 |
| 높음 | 캐시·IP 기록·잠금 객체 상한/정리 부족 | 잘못된 경주 URL 20개에 잠금 20개 잔존 | TTL, 개수/바이트 상한, 실패·취소 시 정리 |
| 높음 | 다른 봇의 다운로드 지속 | 운영 로그의 AhrefsBot 117회, 약 3.12MB | 공통·비싼 경로·다운로드별 제한 |
| 높음 | 조회/응답 비용 상한 부족 | 비압축 요청 허용, 필터 및 경로 반복 가능 | 입력 복잡도·응답량·동시 작업 상한 |
| 중간 | 차트 HTML 직접 삽입 | horseName 등 innerHTML 보간 | 안전한 DOM 생성 및 textContent |
| 중간 | 광범위한 배포 권한 | 배포 계정 roles/editor | 후속 단계에서 최소 권한 검토 |

헤더 우회와 메모리 잔존은 로컬에서 확인했다. 운영 우회 공격 또는 XSS 악용을 실행하거나 확인한 것은 아니다. 봇 이름은 User-Agent 자기 신고값이다.

## 단계별 진행 순서

1. **앱의 확실한 결함 수정**: IP 신뢰 처리, 제한 기록 및 캐시 상한, 실패·취소 시 잠금 정리, 의미 없는 쿼리로 캐시 분할 방지, XSS 지점 제거.
2. **비싼 기능의 사용량 제한**: 상세/분석/통계/API/CSV에 공통 사용량과 별도 다운로드 제한, 입력·필터 범위 검증, 응답 크기 및 동시 처리량 제한.
3. **공개 범위와 인증 설계**: 작은 소개·요약은 공개, 상세/대량 이력/내보내기는 서버 인증. 인증 응답 공유 캐시 금지.
4. **엣지 방어와 우회 차단**: CDN/WAF를 선택하고 Cloud Run 직접 접근을 통제. 비용과 오탐을 검토.
5. **비용 감시 및 재개**: Spend cap 제공 여부·한도 확정, 바이트·요청·오류·DB 지표 확인 후 제한적으로 재개.

## 위임과 감독

사용자 요청에 따라 세 서브에이전트를 모두 `gpt-6-luna`, reasoning `high`로 실행한다.

| 담당 | 소유 범위 | 감독 기준 |
|---|---|---|
| security_core | 앱 미들웨어, 새 security 도우미, Docker 실행 설정, 전용 테스트 | 프록시 우회·메모리 상한·동시성·취소 처리 |
| workload_policy | 새 요청 정책 모듈과 전용 테스트 | 경로 교대 우회·필터 폭증·정상 사용 보존 |
| frontend_xss | race-chart.js, insights.js 및 전용 회귀 테스트, 독립 백엔드 검토 | 악성 문자열의 실제 렌더링 검증 및 정책 우회 검토 |
| 주 에이전트 | 문서, 기존 Vary 테스트 갱신, 통합 코드 검토·테스트 | 기능 회귀, 정책 빈틈, 미완료 항목 명시 |

파일 소유권을 분리한다. 앱 파일 통합은 security_core만 수행하고 요청 정책은 workload_policy와 합의한 인터페이스로 연결한다. 주 에이전트는 최종 검토에서 발견한 문제를 수정 지시하거나 통합 수정한다.

## 완료 판정 기준

- 임의의 XFF 접두부나 다른 비신뢰 IP 헤더로 제한 키를 바꿀 수 없다.
- 신뢰 프록시 미설정 시 직접 연결 peer를 사용한다. 운영 프록시 CIDR을 추측하거나 `*`로 신뢰하지 않는다.
- 공격자가 새로운 IP 기록을 채워 기존 활성 제한을 초기화할 수 없다.
- 캐시·제한 기록·잠금 자료구조가 설정 상한을 넘지 않으며 에러·취소 후 잠금이 해제된다. 잠금은 고정 개수 풀로 두어 임의의 URL별 객체가 누적되지 않는다.
- 쿼리 순서나 무관한 파라미터가 같은 결과의 캐시를 무제한 분할하지 않는다. 실제 표시 결과에 영향을 주는 값은 구분한다.
- 상세/분석/API 경로를 번갈아 호출해도 공통 사용량 제한이 유지된다.
- 비압축 응답도 같은 크기 상한을 적용한다. 응답을 무제한으로 먼저 모은 뒤 검사하지 않는다.
- HTML 삽입 문자열이 텍스트로 표시되며 차트 상호작용은 유지된다.
- gzip과 데스크톱/모바일 렌더링 및 일반 조회가 기존 테스트를 통과한다.
- 운영 비공개 설정을 바꾸지 않는다.

## 추가 점검 및 남는 위험

- 운영 DB 최소 권한, 쿼리 실행시간·실행계획, 의존성 취약점, 계정 감사, 전체 비밀정보 노출 검사는 별도 범위다.
- 프로세스 메모리 기반 제한은 여러 인스턴스 간 전역 한도가 아니며 재시작 시 초기화된다.
- 응답 상한은 생성 완료 전에 수행된 DB/템플릿 작업의 비용을 소급 제거하지 않는다. 입력·동시성 제한을 함께 적용해야 한다.
- TLS 종료 프록시 뒤에서는 검증된 프록시 설정이 HTTPS URL 생성과 사용자 IP 구분을 모두 보장하는지 재공개 전 확인한다.
- 최대 인스턴스 수, gzip, 앱 속도 제한만으로 청구액 상한을 보장할 수 없다. 저장소·로그·DB 등은 별도 비용 경로다.

## 실행 결과

1·2단계를 로컬 소스에 구현했다. 운영에는 재배포하지 않았으며 기존 Cloud Run 비공개 설정을 변경하지 않았다.

### 구현된 제한과 기본값

| 항목 | 기본값 및 동작 |
|---|---|
| 프록시 신뢰 | 프로세스 환경변수 `TRUSTED_PROXY_CIDRS`; 기본값은 신뢰 없음. 직접 연결 peer가 신뢰 CIDR에 있을 때만 오른쪽부터 XFF 체인을 검증해 client 결정 |
| Uvicorn | `--no-proxy-headers`를 명시해 기존 `FORWARDED_ALLOW_IPS` 환경변수와 상관없이 앱이 원래 peer를 검증 |
| 일반 요청 제한 | 기존 사용자 180회/분·60회/10초, 크롤러 30회/분·10회/10초 유지 |
| 일반 제한 기록 | 최대 4,096개, 유휴 120초 정리. 포화 시 새 식별자는 제한된 공통 overflow 기록을 사용하며 기존 활성 기록을 지우지 않음 |
| 비싼 경로 공통 제한 | 같은 client의 대시보드·분석·상세·목록·예측·검증·거리 통계·데이터 상태를 합쳐 24회/분·8회/10초 |
| CSV | 공통 제한에 더해 6회/분·2회/10초 |
| 경로 정책 기록 | 앱별 분리, 최대 8,192개 client/category 기록. 포화 시 새 기록 생성 거부, 만료된 기록만 회수 |
| 동시 처리 | 프로세스당 16개. 캐시 생성 잠금 대기도 포함하며 처리·응답 버퍼링 완료/실패/취소 시 반환. 초과는 작은 503 + Retry-After |
| 응답 크기 | 압축 전 본문 최대 2MiB. Content-Length 사전 확인 및 길이가 없는 스트림의 점진적 검사, 초과 시 작은 413 |
| 응답 캐시 | 최대 128개·본문 합계 4MiB, 항목당 512KiB, TTL 20초 |
| 데이터 객체 캐시 | 최대 128개·추정 보유량 8MiB, 항목당 1MiB. slotted dataclass 내부도 측정하며 너무 큰 객체/복잡한 객체는 캐시하지 않음 |
| 잠금 풀 | 동기 128개·비동기 256개 고정 stripe. URL 수에 따라 객체가 늘어나지 않음 |
| 입력 길이 | 경로 1,024 bytes, 분석/CSV/구형 모바일 쿼리 4,096 bytes, 나머지 쿼리 2,048 bytes |
| 조회 기간 | 분석·CSV·검증에서 기간을 지정하면 시작/종료일을 함께 입력. 두 날짜 차이는 최대 366일. 둘 다 없으면 기존 기본 조회 유지 |
| 목록·이력·말 필터 | 목록 최대 200페이지, 이력 설정 1~60, 말 필터 최대 40개. 기존 loader의 결과 행수 제한은 유지 |

`/races/+1`처럼 프레임워크가 숫자로 받아들이지만 제한 분류에서 빠질 수 있던 ID 표현을 거부하고, 경주 ID는 양의 ASCII 십진수·signed 64-bit 범위로 검증한다. 일반적인 공식 ID의 앞자리 0은 보존한다.

대시보드 `meet`는 빈 값 또는 경마장 코드 1~4만 허용하고, 개체 상세 URL의 숫자 ID도 내부 ID 변환 시 DB 정수 범위를 넘지 않도록 확인한다. 거대한 숫자로 DB 오류를 반복 발생시키는 입력은 조회 전에 422로 거부한다.

입력 오류는 422, 사용량 초과는 429 + Retry-After 60이다. 각 한도는 프로세스 단위 보호이며 월 청구액이나 여러 인스턴스의 합산 사용량 보장이 아니다. 객체 캐시의 byte 값은 Python 객체 추정치이고 프로세스 전체 RSS 상한이 아니다. 이 한도들은 소규모 서비스용 초기값이며 재개 전 정상 사용자 흐름으로 오탐을 확인해야 한다.

### 캐시와 화면 안전성

- 실제 결과에 영향을 주는 쿼리만 정렬해 캐시 키에 반영한다. 선택 경주·주행심사 ID, 모바일/데스크톱, origin, 쿼리 유무에 따른 noindex 차이는 유지한다.
- 쿠키·Authorization이 있는 요청과 Set-Cookie 응답은 응답 캐시에서 제외한다. 이는 로그인 구현 자체가 아니며 현재 앱에는 사용자 인증이 추가되지 않았다.
- UA 차단 403은 `no-store`로 변경했다. gzip을 유지하고 기존 Vary 헤더도 보존한다.
- `race-chart.js`는 동적 텍스트를 `textContent`로 표시하고, `insights.js`는 HTML/속성 이스케이프 및 숫자 검증을 적용했다.
- 시작/종료일을 함께 입력해야 한다는 안내를 분석·검증 화면에 추가했다.

### 감독 과정에서 추가로 보완한 사항

초기 구현 검토에서 활성 IP 기록 제거로 제한이 초기화되는 문제, 앱 간 제한 상태 공유, 선택 경주 ID가 빠진 캐시 키, 검색 태그가 섞이는 캐시, 만료 요청 타임스탬프 누적, 한쪽 날짜만 준 기간 우회, 비정규 숫자 ID 경로 우회, slotted dataclass 크기 누락 및 초과 크기 추정치가 다시 캐시되는 문제를 발견해 수정 지시했다. 별도 통합 테스트로 압축 여부와 무관한 응답 상한, 다중 Set-Cookie 보존, 신뢰 프록시만 HTTPS 설정 가능, 동시 처리 초과 및 취소 후 자원 반환을 확인한다.

### 재개 전 남은 조건

1. 실제 TLS 종료 프록시의 연결 peer·XFF 동작을 검증하고 최소 범위의 `TRUSTED_PROXY_CIDRS`를 배포 환경에 설정한다. 빈 값 그대로 프록시 뒤에 배포하면 사용자가 같은 peer로 묶여 429가 발생하고 HTTP 자산 URL이 생성될 수 있으므로 재공개 조건으로 확인한다. `*` 또는 임의의 광범위 CIDR로 해결하지 않는다.
2. 현재 2MiB 응답 상한과 200페이지 제한 때문에 큰 페이지/깊은 목록은 거부될 수 있다. 큰 데이터를 계속 제공하려면 페이지 분할·요약·별도 인증 내보내기를 설계한다.
3. 엔티티 목록의 전체 RaceEntry 집계, 예측 원장/검증의 과거 데이터 조회 등 쿼리 자체의 비용은 남아 있다. 이번에는 진입 빈도와 동시성/출력 크기를 제한했으며 DB 쿼리 최적화·최소 권한·statement timeout은 별도 검토가 필요하다.
4. 3~5단계의 서버 인증, 엣지 차단, 원본 우회 차단, 비용 감시를 결정한다. 고정비가 생기는 인프라는 이번 작업에서 만들지 않았다.

### 검증 기록

- 최종 Python 웹·보안 회귀 테스트 **137개 통과**: 새 보안/정책/통합 테스트와 기존 대시보드, 분석, 거리 페이지, 영상 URL, 구간 표시, 아카이브, 포맷 테스트.
- 실제 프런트엔드 IIFE를 실행하는 Node XSS 회귀 테스트 **2개 통과**.
- 변경 Python 파일 `ruff check` 및 `git diff --check` 통과.
- 기존 Starlette/httpx 사용에 대한 deprecation warning 1건은 남아 있으며 실패는 없다.
- 정상 화면을 여러 개 연달아 확인하는 기존 테스트 2개는 실제 대기 대신 요청별 3초 경과를 모의하도록 수정했다. 별도 보안 테스트는 기본 8회/10초 제한을 그대로 검증한다.
- 운영 DB 및 외부 서버에는 부하 테스트를 실행하지 않았다. 전체 모델 학습·연구 테스트는 이번 웹 보안 수정 범위에서 실행하지 않았다.
