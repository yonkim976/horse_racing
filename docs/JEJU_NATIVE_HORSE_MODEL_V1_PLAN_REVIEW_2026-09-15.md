# 제주마 예측모델 V1 계획 검토·개정 보고서

작성일: 2026-09-15 (Asia/Seoul)

## 결론

**말의 능력·상태를 먼저 만들고 같은 경주의 상대들과 경쟁시키는 기본 방향은 유지한다. 다만 모집단에 실제 오류가 있었고, 시점·비교실험·성능 판정 규칙을 더 구체화해야 했다.** 이를 반영해 [실행 지시문](JEJU_NATIVE_HORSE_MODEL_V1_AGENT_PROMPT_2026-09-15.md)을 `jeju_native_horse_v1_plan_r2`로 개정했다.

이번 작업은 사용자가 요청한 문서 검토·계획 수정이다. 연구 DB는 읽기 전용으로 확인했으며 새 모델 fit, 역사 성능 재평가, 운영 변경은 실행하지 않았다. 아래 수치 중 DB 모집단 수량은 직접 조회한 사실이고, fit 예산·비열등 허용폭·미래 평가 표본 수는 **새로 제안해 계획에 고정한 설계값**이다. 예측률 개선의 실측값이 아니다.

## 1. 가장 중요한 발견: 상대마와 우승마를 빼고 평가할 위험

기존 문서의 `9,288경주·90,177행`은 **공식 연결 완료 출발행의 합계**였으며 모든 출발마의 ID가 완결된 경주 집합이 아니었다.

| 확인 항목 | 실측 |
|---|---:|
| 양수 정상 결과 경주의 원천 출전행 | 90,892 |
| 미출주 93/94/95 | 690 |
| ID 연결을 필터하기 전 실제 출발행 | 90,202 |
| 실제 출발 중 공식 연결 미해결 | 25 |
| 기존 연결 완료 출발행 | 90,177 |
| 미해결 출발마가 있는 경주 | 8 |
| 그 8경주의 전체 출발행 | 80 = 완료 55 + 미해결 25 |
| 미해결 출발 중 1착 행 | **3** |
| 8경주 전체 격리 후 완결 집합 | **9,280경주·90,122행** |

미해결 행만 지우면 어떤 경주는 승자가 사라지고, 다른 경주는 실제로 경쟁한 상대가 빠진다. 승자가 남아 있어도 줄어든 편성에 확률을 다시 나누므로 실제 경주 확률 평가와 달라진다. 이름으로 ID를 보완하지 않고, **경주 전체의 출발집합이 완결됐는지 먼저 검사**하도록 변경했다.

DB 내부 race ID는 이 snapshot에만 대응한다.

| race_id | 경주일 | 출발마 | 미해결 출발마 | 미해결 우승마 |
|---|---|---:|---:|---:|
| 5111 | 2019-05-03 | 10 | 1 | 0 |
| 5065 | 2019-05-25 | 10 | 1 | 0 |
| 5040 | 2019-06-08 | 10 | 1 | 0 |
| 4983 | 2019-07-12 | 10 | 1 | 0 |
| 9038 | 2026-07-07 | 10 | 6 | 0 |
| 9039 | 2026-07-07 | 10 | 4 | 1 |
| 9040 | 2026-07-07 | 10 | 6 | 1 |
| 9041 | 2026-07-07 | 10 | 5 | 1 |

위 날짜는 DB 원천에 저장된 값이며, 이번 검토에서 실제 개최일을 별도로 재검증했다는 뜻은 아니다. 미해결 사건은 기존 격리 원장에 따라 보존한다.

완결성 적용 후 정상 완주 89,905행, DQ 162행, DNF 55행이며 우승자 없는 경주는 0개다. 2025 개발 구간은 715경주·6,953행으로 그대로이고, 2026 역사 평가 후보는 514경주·4,871행에서 **510경주·4,852행**으로 바뀐다. 이 수량은 현재 거리 target 등 추가 계약 전 기준이다.

## 3. 100%를 향한 성능 관리

전체 경주에서 한 마리를 고르는 **Top1**을 사용자 목표로 삼고, 확률이 얼마나 정확한지는 **NLL·Brier·확률 보정**으로 확인한다. 확률을 99%라고 과장해 맞힌 몇 경주보다, 전체 경주에 대해 실력을 정직하게 측정하고 틀린 원인을 줄이는 과정이 필요하다.

기존 V2의 179경주 Top1 32.96%는 다른 모집단·시점의 참고값이다. 새 모델도 그 수준이라는 의미가 아니며, 새 모집단에서 U0/Elo/속도/공식 레이팅과 동일 경주로 다시 비교해야 한다.

계획상의 판정 기본값:

- **주 지표:** 경주당 winner-set NLL. **목표 대시보드:** 전체 경주 Top1·적중 수·분모·구간.
- **우월성:** 후보−기준 NLL 차이의 경주/경주일 bootstrap 95% CI 상한이 모두 0 미만.
- **비열등 허용폭:** NLL +0.01 nat/경주, Top1 −1%p. 실행 전 봉인하는 연구 선택이며 ‘이 정도면 충분히 좋다’는 실측 근거가 아니다.
- **선택 경주:** 전체 지표를 항상 유지하고 자신 있는 경주의 적중률에는 coverage를 병기.
- **미래 평가:** 기본 연속 300개 적격 경주 및 최소 30개 경주일. 시작 전 검출 가능한 개선폭을 계산하며 표본 부족 시 확대.

100%는 장기 목표로 유지하지만 유한 표본의 무오류는 미래 확률 100%를 증명하지 않는다. 이 때문에 작은 집단의 100%에도 구간과 선택 규칙을 기록한다. 비율 구간 계산에는 [SciPy의 exact confidence interval](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.binomtest.html)을 사용할 수 있으며, 경주 사이 독립성 가정의 한계는 따로 보고한다.

## 4. 실행 순서와 우선 투자

1. **P0~P1: 모집단·시점·상태 데이터셋.** 현재 가장 큰 위험인 불완전 경주와 공개시점 가정을 먼저 통제한다.
2. **P2: 단순 기준선과 H0.** Elo와 단순 속도를 이기지 못하면 복잡한 구조의 성능 가치를 다시 판단한다.
3. **P3: H1~H3와 이력 비교.** 시간/구간·조교/심사/진료/과거 체중·이번 경주 조건을 단계별 검증한다.
4. **P4~P5: 후보 선택과 동결 역사 평가.** 2025로 선택하고 2026은 고정된 후보를 한 번 평가한다. 이미 사용된 2026을 완전한 독립 test로 표현하지 않는다.
5. **P6: 실제 사전 예측 원장 연결 준비.** 로컬 schema/CLI/replay 테스트를 만든다. 실제 미래 경주 사전 기록을 시작한 시점부터 새로운 검증을 쌓는다.
6. **후속 성능 확장:** 상대 편성·전개 → 기수/말×기수/마방 → T-30 정보 → 성능분포/위험/앙상블. 같은 시각 시장 정보가 확보되면 시장 대비 추가 정보도 별도 측정한다.

큰 모델이나 무제한 탐색부터 시작하지 않는다. 기존 프로젝트에 동적 상태·속도·LightGBM·순위확률 코드가 있으므로 계약에 맞는 부분을 재사용한다. 다만 기존 LightGBM 경로는 fit/tune/calibration을 합친 `train_all`에서 encoder를 적합하므로 새 연구의 엄격한 FIT 전용 전처리에 맞게 분리해야 한다. 이는 기존 성능 전체가 무효라는 판정이 아니라 **새 계약에 그대로 복사할 수 없는 코드 경계**다.

전처리는 학습 구간으로만 적합해야 한다는 원칙은 [scikit-learn 공식 누수 방지 지침](https://scikit-learn.org/1.8/common_pitfalls.html)을 확인했다. 후보 선택에 사용한 결과의 낙관적 편향과 선택/평가 분리 원칙은 [공식 모델 선택 예제](https://scikit-learn.org/1.5/auto_examples/model_selection/plot_nested_cross_validation_iris.html)를 참고했다. 문서의 분기별 날짜·예산·허용폭은 이 프로젝트에 맞게 제안한 설계이며 외부 문서가 정한 값은 아니다.

## 5. 확인한 범위와 재현 근거

읽은 자료: 원 실행 지시문, 말 능력 기본 설계, 제주마 준비도/전체 DB 보고서, 기존 제주 V1/V2, dataset/동적 상태/LightGBM/Plackett–Luce 관련 코드, DB 생성 스키마.

DB SHA-256을 직접 재계산해 기준값과 같음을 확인했다.

```text
0f2871c2a8f931bb968d8bf7086c27f0644c0ef7332b41b7a1bd85ff637c638f
```

무결성 전체 감사나 모든 원천 재수집을 다시 실행하지 않았다. 문서의 핵심 모집단 주장과 의심된 경계만 읽기 전용 SQL로 확인했다. 재현 시 SQLite를 `file:...sqlite3?mode=ro`, `uri=True`로 열고 다음을 실행한다.

```sql
WITH starters AS (
    SELECT v.id AS race_id, v.event_date, e.identity_status,
           e.finish_position
    FROM event v
    JOIN entry e ON e.event_id = v.id
    WHERE v.event_type = 'race'
      AND v.population_status = 'confirmed_native_normal_race'
      AND (e.finish_position BETWEEN 1 AND 89
           OR e.finish_position IN (91, 92))
), bad AS (
    SELECT DISTINCT race_id
    FROM starters
    WHERE identity_status != 'official_race_ids_linked'
)
SELECT COUNT(DISTINCT race_id) AS races, COUNT(*) AS starters,
       SUM(finish_position BETWEEN 1 AND 89) AS normal,
       SUM(finish_position = 91) AS dq,
       SUM(finish_position = 92) AS dnf
FROM starters
WHERE race_id NOT IN (SELECT race_id FROM bad);
-- 9280 | 90122 | 89905 | 162 | 55
```

`WHERE race_id IN (SELECT race_id FROM bad)`로 바꾸면 8경주·80출발행이다. 미해결 행만 세면 25행, 그중 `finish_position=1`은 3행이다. DB 날짜는 `YYYYMMDD` 형식이며 2025-12-28~12-31 경주는 0건이다.
