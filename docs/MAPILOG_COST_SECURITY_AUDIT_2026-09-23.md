## 3. 재공개 전 보완할 코드 문제

### 우선: IP 헤더 신뢰 문제와 제한 우회

`src/horse_racing/web/app.py:85`는 `X-Forwarded-For`의 첫 값을 그대로 제한 키로 사용한다. 로컬 TestClient에서 같은 클라이언트의 일반 크롤러는 11번째 요청이 429였지만, 헤더 앞부분만 바꾼 20회 요청은 모두 200이었다. 운영 환경에 대한 우회 공격 테스트는 하지 않았다.

실제 프록시 구성을 고정하고 신뢰된 프록시가 검증/덮어쓴 주소만 사용해야 한다. 단순히 임의의 n번째 주소를 고르는 수정은 피한다. Docker 실행 인자의 `--forwarded-allow-ips='*'`도 이 신뢰 모델과 함께 재검토해야 한다. Google 외부 로드밸런서는 기존 XFF 앞부분을 검증하지 않는다고 명시한다. 직접 Cloud Run 경로의 헤더 처리는 별도로 확인해야 한다. [Google XFF 문서](https://docs.cloud.google.com/load-balancing/docs/https#x-forwarded-for_header)

User-Agent를 브라우저처럼 바꾸거나 여러 IP를 사용하면 현재 봇별 제한도 약해진다. 프로세스 메모리 기반 제한은 인스턴스 간 공유되지 않고 재시작하면 초기화된다. 엣지 IP 제한에 더해 로그인 계정별 사용량, 비싼 경로별 한도, 전체 처리량 제한이 필요하다.

### 우선: 캐시와 제한용 자료구조의 메모리 증가

- `app.py:227`: 원본 쿼리 문자열 전체가 캐시 키라 의미 없는 파라미터 변경으로 캐시를 우회할 수 있다.
- `app.py:161`, `app.py:282`: 256/128은 용량 상한이 아니라 만료 항목 청소를 시작하는 기준이다. 아직 유효한 항목은 그 이상으로 늘어날 수 있다.
- `app.py:242`: 잘못된 경주 경로에도 lock을 만든다. 로컬에서 서로 다른 잘못된 경주 URL 20개를 요청한 뒤 성공 응답 캐시는 0개였지만 lock은 20개 남았다. 정상 응답 캐시에 들어가지 않은 key의 lock 정리 경로가 없다.
- IP별 요청 bucket도 전체 만료·삭제가 없다. 헤더 조작이나 많은 실제 클라이언트로 키가 지속 증가할 수 있다.

메모리 부족·재시작·캐시 손실과 반복 DB 조회로 연결될 수 있다. 개수 및 총 바이트 상한이 있는 TTL/LRU, 모든 상태에서 lock 정리, 쿼리 allowlist와 정규화, IP bucket 정리가 필요하다. lock 정리는 동시 요청 중인 항목을 제거하지 않도록 설계해야 한다.

### 우선: gzip은 비용 상한이 아니다

동일 미들웨어에 400KB의 합성 응답을 추가한 로컬 검사에서 `Accept-Encoding: gzip`은 압축됐지만 `identity`는 400,000 bytes를 그대로 반환했다. 실제 운영 데이터를 조회하거나 공개 서버에 부하를 주지 않은 검사다.

비압축 요청, 수많은 서로 다른 페이지, 정적 파일, CSV/API 다운로드가 남아 있다. 앱 내부 캐시는 DB 작업을 줄여도 매 요청의 인터넷 전송 자체를 없애지는 않는다. HTML에 한 번에 넣는 이력 축소, 페이지 분할, 데이터 응답 크기 제한, 다운로드별 사용량 제한, 공개 콘텐츠의 CDN 캐싱이 필요하다. 지연 로딩을 추가해도 그 데이터 API가 공개·무제한이면 방어가 되지 않는다.

### 추가 보안: 외부 데이터의 HTML 삽입

`src/horse_racing/web/static/js/race-chart.js:108`, `:413`에서 `horseName` 등의 데이터를 `innerHTML` 문자열에 직접 삽입한다. 수집 데이터/DB가 오염될 경우 저장형 DOM XSS로 연결될 수 있는 지점이다. `tojson`은 JSON 스크립트 삽입을 보호하지만 이후 `innerHTML` 사용을 안전하게 만들지는 않는다. 현재 CSP는 `script-src 'unsafe-inline'`을 허용한다.

텍스트에는 `textContent`를 사용하고 DOM을 명시적으로 구성하는 방식으로 바꾼다. 외부 사용자가 해당 데이터를 직접 쓰는 경로와 실제 악용은 확인하지 않았다. 이번 비용 사고가 XSS나 침해 때문이라는 증거는 없다.

### 권한 및 운영 안전성

- 런타임은 별도의 `mapilog-cloud-run` 서비스 계정을 사용하고 DB URL은 Secret Manager 참조다. 비밀 값은 출력하지 않았다.
- 프로젝트 기본 Compute 서비스 계정에는 `roles/editor`가 있다. 이전 배포 수정 주체도 이 계정이었다. 빌드·배포 권한을 필요한 범위로 축소하는 것이 좋다. 운영 런타임 계정에 Editor가 있다고 확인한 것은 아니다.
- HTTP 요청 timeout은 300초다. 비싼 조회 경로와 느린 요청의 자원 점유를 줄일 수 있도록 경로별 처리시간·DB 실행 제한을 검토한다.
- API/CSV와 상세 페이지에 로그인 검증은 없다. 화면만 로그인으로 감추는 변경은 충분하지 않다.
- 로그인 도입 시 기존 응답 캐시는 사용자 구분이 없으므로 인증 응답을 공유 캐시에서 제외해야 한다.
- UA에 따라 나오는 403에 현재 `public, max-age=86400`이 붙는다. 향후 CDN에 403 캐싱을 허용할 경우 일반 사용자에게 차단 응답이 재사용되지 않도록 `no-store` 또는 정확한 캐시 분리를 적용한다.

## 4. 비용 제한에 대한 최신 확인

일반적인 **Alerts-only budget은 자동 중단 기능이 아니다**. 최신 공식 문서에는 **Cloud Run을 지원하는 Spend cap budget (Preview)** 이 별도로 안내되어 있다. 지정 프로젝트·서비스의 예산 도달 시 신규 사용을 중단하지만, 집계 지연과 처리 중 요청 때문에 초과 청구 가능성이 있으며 고정/저장 비용도 남는다. 정확한 원화 금액에서 실시간으로 멈추는 보장은 아니다. [Spend cap 공식 문서](https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps), [일반 예산 알림](https://docs.cloud.google.com/billing/docs/how-to/budgets)

이번에는 사용자 요청 중 **즉시 일시 중단**을 선택해 적용했다. 금액 상한이나 예산 알림을 새로 만들지는 않았다. Billing Budget API가 Mapilog 프로젝트에서 비활성 상태여서 기존 예산 목록도 확인하지 못했다. 이를 예산이 없다는 증거로 해석하면 안 된다. 다른 프로젝트의 API나 예산은 변경하지 않았다.

재개 전에 해당 결제 계정에서 Spend cap 제공 여부와 금액을 확정하고, Cloud Run 외에 CDN·로그·DB·저장소 비용도 별도 감시한다. 요청 수뿐 아니라 분당/일별 응답 바이트, 캐시 미스, 5xx, 메모리, DB 지연을 감시하고 서비스 비공개 전환 수단을 유지한다. 최대 인스턴스 수는 전송량이나 청구액 상한이 아니다.

## 5. 랜딩 페이지와 로그인 효과

| 방안 | 기대 효과 | 남는 문제 |
|---|---|---|
| 기존 서버의 메인 HTML만 작게 변경 | `/`의 전송량 감소 | 알려진 상세/API 주소는 계속 크롤링 가능 |
| 작은 정적 랜딩을 CDN에서 제공 | 원본 서버 호출과 공개 전송량 감소 | 데이터 경로와 원본 우회가 열려 있으면 계속 비용 발생 |
| 상세/분석/API/CSV의 서버 인증 | 비회원 크롤러의 비싼 데이터 조회 방지 | 로그인 화면 공격·자동 가입·도용 계정·로그인 봇 대응 필요 |
| CDN/WAF에서 먼저 차단 | 차단된 요청이 앱/DB까지 도달하지 않음 | 플랜 비용·오탐·분산 봇 및 우회 경로 관리 필요 |

Mapilog에는 **작은 공개 정적 랜딩 + 선택한 공개 요약만 CDN 캐시 + 상세/분석/내보내기는 서버 인증 + 엣지 봇 차단** 구성을 권한다. 검색 노출은 공개 소개·요약에서 유지하고, 과거 전체 이력은 보호한다. 로그인 전 화면의 JS가 비공개 데이터를 미리 다운로드하지 않도록 한다. 인증·가입·비밀번호 재설정에도 제한과 필요 시 CAPTCHA를 적용한다.

## 6. 대규모 사이트가 사용하는 방어 방식과 선택지

대형 서비스에서 쓰이는 구조는 CDN 캐싱, WAF/DDoS 방어, 행동 기반 봇 판별, 조건부 challenge, IP·계정·경로별 제한, 서버 인증, 원본 직접 접근 차단을 조합하는 방식이다. 공개 HTML 크기 하나나 로그인 하나만으로 모든 봇을 막을 수는 없다.

1. **Cloudflare 계열**: 무료 Bot Fight Mode와 관리형 AI 봇 차단부터 검토할 수 있다. Ahrefs 같은 비AI 크롤러는 별도 정책이 필요하다. HTML/JSON은 기본 캐시 대상이 아니므로 공개 페이지만 캐시 규칙을 만들어야 한다. 보호된 내용과 인증 응답은 공유 캐시에 넣지 않는다. 무료 모드에는 세부 예외 제약과 오탐 가능성이 있다. 프록시 DNS 설정만으로 Cloud Run 원본 우회가 차단되지는 않는다. 별도의 원본 인증/네트워크 보호 설계가 필요하다. [Bot Fight Mode](https://developers.cloudflare.com/bots/get-started/bot-fight-mode/), [관리형 봇 설정](https://developers.cloudflare.com/bots/additional-configurations/custom-rules/), [기본 캐시 동작](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/)
2. **Google Cloud 구성**: 외부 Application Load Balancer + serverless NEG + Cloud Armor, 필요 시 Cloud CDN. Cloud Run ingress는 `internal-and-gclb`로 제한하고 기본 주소 등 우회 경로를 닫는다. 한국 전용 차단은 보조 수단이며 국내 프록시나 국내 봇은 남고 해외 사용자·검색 봇은 차단될 수 있다. [공식 통합 문서](https://docs.cloud.google.com/armor/docs/integrating-cloud-armor)

Cloud Armor Standard에는 정책·규칙·요청 비용이 있고 LB/CDN도 별도 과금된다. 소규모 서비스에서는 추가 고정비가 현재 사고 비용과 비슷하거나 더 커질 수 있어 견적 후 선택해야 한다. Cloud Armor 속도 제한도 근사치여서 엄밀한 전역 사용량 한도나 금액 한도로 쓸 수 없다. [가격](https://cloud.google.com/armor/pricing), [속도 제한의 정확도](https://docs.cloud.google.com/armor/docs/rate-limiting-overview)

허용할 검색 봇은 User-Agent 이름만 믿지 말고 공식 IP 범위 또는 검증된 봇 신호를 사용한다. 정상 봇에도 합리적인 이용량 제한은 유지한다. [Google 봇 검증](https://developers.google.com/search/docs/crawling-indexing/googlebot)

## 7. 검증 범위와 미완료 항목

- 운영: IAM/ingress 변경과 네 주소 차단 확인, 요청 로그 표본 확인, 리소스 설정 확인.
- 로컬: 기존 Claude 및 일반 크롤러 제한 테스트 2개 통과. DB 접근 없는 별도 검사에서 XFF 우회, 실패 URL lock 잔존, 압축 선택 동작 재현.
- 대시보드 테스트: 34개 중 30개 통과, 4개 실패. 실패는 기존 테스트가 `Vary == User-Agent`만 기대하지만 gzip이 `Accept-Encoding`을 추가하기 때문이다. 기대 헤더를 집합으로 검증하도록 정리할 필요가 있다.
- 인수 문서에 있던 마이그레이션 타입 오류는 현재 파일에서 이미 `sa.types.TypeEngine`으로 바뀌어 있으며 이번 대시보드 테스트에서 마이그레이션은 실행됐다. 이번 작업에서 마이그레이션을 수정하지 않았다.
- 기존 애플리케이션·연구·DB 변경 파일은 수정/초기화/커밋하지 않았다. 발견한 앱 보완사항은 아직 구현·배포하지 않았다.
- 운영 DB 권한/RLS·데이터 유출·전체 계정 감사·의존성 취약점 전수 검사는 수행하지 않았다. 현재 결과를 전체 보안 무결성 보증으로 해석하면 안 된다.
