# 서울 경주기록 저장 감사 · 2026-09-08

> 이 문서는 복원 전 감사 상태입니다. 후속 복원·검증 결과는 [서울 구간기록 복원 보고서](SEOUL_SECTION_REPAIR_2026-09-08.md)를 참고하세요.

## 범위와 방법

현재 `data/horse_racing.sqlite3`를 읽기 전용으로 조회했다. 완료 경주 11,871개, 출전/결과 129,122건, 구간 행 432,705개가 대상이다. 보유 기간은 2015-01-03~2026-09-06이며, 모든 연도·경주를 빠짐없이 수집했다는 뜻은 아니다. 주행심사는 별도 데이터로 이번 정규 경주 집계에서 제외했다.

보관 dacom11 보고서 913개와 API4_3 원본 응답 174개를 대조했다. 겹치는 경우 최신 API 원본을 우선하여 출전 129,122건 모두 원본과 연결했다. 비교 기준은 과거 보고서 110,345건, API 18,777건이다. 과거 성적표의 고정폭 시간 셀을 독립적으로 추출하여 현재 파서의 숫자 당김 오류를 재현하지 않도록 했다. 전체 DB 재저장이나 웹 변경은 수행하지 않았다.

별도 공식 웹 확인: [서울 용어해설](https://race.kra.co.kr/raceScore/scoretableLayerExplanation.do?meet=1), [2024-10-05 서울 5R 공식 성적표](https://race.kra.co.kr/globalEn/resultsRaceDetailSeoul.do?rcDate=20241005&rcNo=5). 최신 거리별 웹 성적표 재조회는 성공하지 못했으므로 전체 대조 근거는 보관 공식 원본이다.

## 발견한 문제

1. 과거 원문에 존재하는 코너 시간 **265,607개**가 DB에 없다. 1C 21,698개 / 2C 23,219개 / 3C 110,345개 / 4C 110,345개. 서울 dacom11 파서가 G3F·S1F·G1F만 저장하는 분기이기 때문이다.
2. 과거 원문에 존재하는 지점별 통과순위 **486,251개**가 구조화된 `position`에 없다. S1F·3C·4C·G1F 각각 110,334개, 1C 21,697개, 2C 23,218개다. 기존 `group_notation_raw`에 보존된 문자열을 활용할 수 있다. 누락 시간과 순위는 동일 구간 행에 함께 들어갈 수 있으므로 합계를 추가할 행 수로 해석하면 안 된다.
3. 잘못 저장된 시간 8개를 확인했다. G1F 2개는 연승 배당 빈칸을 처리하면서 4C 시간으로 잘못 저장했고, 원문 G3F가 `#####`인 4개는 S1F를 G3F로 당겨 저장했다. 이 중 2개는 S1F도 다음 코너 시간으로 밀렸다. `#####`는 유효한 시간으로 복원할 수 없으므로 미제공으로 남겨야 한다.
4. 정상 착순이 있으나 완주기록이 없는 출전 8건은 원문에 기록이 있다. `[부]` 표시를 포함한 긴 마명이 체중 칸에 붙어 있는 형태이며 본문 파서가 처리하지 못한다. 페르디도포머로이 6건, 파이니스트워리어 2건. 말별 G3F/G1F 누적 변환도 완주기록이 없어 제한된다.
5. API 대조 대상은 현재 파서가 사용하는 시간·순위와 DB 사이에 누락/불일치를 발견하지 못했다. 원본 자체의 정확성을 보증하거나 모든 잠재 API 필드를 검사했다는 의미는 아니다.

## 같은 코드에 서로 다른 의미가 저장됨

| 원본 | S1F·코너 시간 | G3F | G1F |
|---|---|---|---|
| 서울 API4_3 | 출발부터 누적 | 출발→결승 600m 전 누적 (`seG3fAccTime`) | 출발→결승 200m 전 누적 (`seG1fAccTime`) |
| 과거 서울 dacom11 | 출발부터 누적 | 마지막 600m 주파시간 | 마지막 200m 주파시간 |

두 의미를 구분하는 컬럼이 구간 테이블에 없다. 웹은 `G3F > G1F` 또는 `G1F < 전체기록/2` 등 수치 관계로 판단해 변환한다. 일반적인 데이터에는 동작하지만 명시적 출처/기록종류 없이 추정하며, 잘못 저장된 값이나 비정상 기록에서 불안정하다. 보완 시 누적·막판 기록을 구분하는 저장 규칙을 먼저 확정해야 한다.

예: 2026-09-06 서울 1R 명성파티는 전체 61.1초, DB G3F 24.7초, G1F 48.5초다. 마지막 600m는 36.4초, 마지막 200m는 12.6초로 계산된다. 반대로 2024-10-05 서울 5R 공식 성적표 우승마는 전체 75.1초, G3F 37.5초, G1F 12.8초이므로 지점 누적은 37.6초와 62.3초다.

거리별로 별도 테이블을 만들지 않고 `races.distance_m`로 구분한다. `race_entries`는 경주와 말을 연결하고, `race_results`에 착순/완주기록, `race_section_results`에 출전 ID × 구간 코드별 1행을 저장한다. 시간은 정수 밀리초다. `distance_from_start_m`는 서울 432,705행 모두 NULL이며, 선두와의 거리차 `gap_to_leader_lengths`도 모두 NULL이다.

| 거리 | 정상 기록에서 제공되는 시간 항목 | 현재 저장 상태 |
|---|---|---|
| 1,000·1,100·1,200·1,300·1,400m | S1F, 3C, 4C, G3F, G1F | 과거 보고서 기반은 S1F/G3F/G1F만, API 기반은 코너도 저장. 1,100m는 과거 17두만 보유 |
| 1,600m | S1F, 2C, 3C, 4C, G3F, G1F | 과거 보고서 기반 2C/3C/4C 누락, API는 저장 |
| 1,700·1,800·1,900·2,000·2,300m | S1F, 1C, 2C, 3C, 4C, G3F, G1F | 과거 보고서 기반 1C~4C 누락, API는 저장 |

이는 거리별 정상 항목 구성이다. 취소/중지 등 특수결과와 원문 미제공 값은 공란일 수 있다. FIN은 구간 테이블에 별도 저장하지 않고 `race_results.finish_time_ms`로 표시한다.

## 서울 화면에 적용해야 할 차이

- 서울은 3C → G3F → 4C 순서다. 공식 일반 용어해설의 기준은 결승 전 810m → 600m → 530m이며 제주처럼 3C/G3F를 같은 지점으로 취급할 수 없다.
- API 유효시간 대조에서 1,000m S1F=3C 420/424건, 1,600m S1F=2C 1,146/1,146건, 1,700m S1F=1C 1,585/1,586건이다. 1,000m 4건 및 1,700m 1건의 원문 불일치가 있어 거리 이름만으로 강제 병합하면 안 된다.
- 특히 1,700m S1F/1C 일치와 공식 일반 해설의 1C 잔여 1,680m를 단순 대입하면 모순이 생긴다. 내·외주로 및 거리별 측정 기준을 별도 확인하기 전 모든 코너에 공통 거리 좌표를 적용하면 안 된다. 이번 감사는 원자료 값과 저장 상태를 확인했으며 거리별 실제 코너 좌표 확정까지 수행한 것은 아니다.
- 현재 서울 화면은 제주 전용 구간 위치/길이 설명을 적용하지 않으며, 마지막 600m 기록을 별도 열로 표시하지 않는다. 서울에 맞는 누적·인접 구간·막판 기록 분리가 필요하다.
- 성적표 하단의 경주 전체 펄롱타임·선두 통과타임은 말별 구간 기록과 다르다. 원문에는 있으나 현재 정규 경주 스키마/파서에 구조화해 저장하지 않는다. 말별 기록만으로 이 표를 대체하면 안 된다.
