# 통과착순·통과조 인수인계 · 2026-09-26

다른 에이전트가 2017–2026 연구 성적표의 말별 통과착순과 경주 단위 통과조를 읽거나 이어서 고칠 때 쓰는 문서다. 성적표 파일 위치와 시간 종류는 [2017–2026 성적표·주행심사 DB](MEET_SCORE_AND_TRIAL_DB_2026-09-25.md)를 본다. 이 문서는 2026-09-26에 연구 DB에 넣은 통과 데이터와, 그 뒤에 확인한 빈 경주의 사유를 기준으로 한다.

## 1. 어디까지 했나

서울·부산·제주 2017–2026 연구 성적표에 통과착순과 통과조를 성적표 기준으로 넣었다. 영천은 2026년 12경주만 있고, 이번 적재에서 다시 쓰지 않았다. 그 12경주에는 통과조 62줄이 이미 있다.

운영 DB `data/horse_racing.sqlite3`, Supabase, 예측 원장, 모델, 웹 구간 조회는 바꾸지 않았다. 커밋하지 않았다. 2016년과 그 이전 성적표 연구 DB는 없다.

연구 성적표는 조회용이다. 모델 입력으로 연결하지 않는다. `data/research/section_point_db_20260925/section_points.sqlite3`와 `section_points_ext.sqlite3`는 쓰지 않는다.

## 2. 어느 파일을 읽나

경마장·연도마다 `data/research/{meet}_{year}_score_20260925/{meet}_{year}.sqlite3`다. meet는 `seoul`, `busan`, `jeju`, `yeongcheon`이다.

| 테이블 | 키 | 내용 |
|---|---|---|
| `section_time` | `(meet_code, race_date, race_number, kra_horse_id, point_code, time_kind)` | 말별 구간 시간과 통과착순. 같은 지점의 누적과 막판이 두 행으로 있을 수 있다 |
| `passing_group` | `(meet_code, race_date, race_number, point_code)` | 경주 단위 통과조. `notation_raw`가 성적표 문자열이다 |

빈 값, `-`, `X`는 통과조로 넣지 않는다. 경주 전체 3F·4F 통과시간은 넣지 않는다. 성적표에 없는 출전마의 API 행은 세지 않고 건너뛴다.

적재 스크립트:

| 경마장 | 스크립트 | 다시 실행 |
|---|---|---|
| 서울 | `scripts/load_seoul_point_passing.py` | `PYTHONPATH=src .venv/bin/python scripts/load_seoul_point_passing.py --year YYYY` |
| 부산 | `scripts/load_busan_point_passing.py` | 같은 방식 |
| 제주 | `scripts/load_jeju_point_passing.py` | 같은 방식 |

API가 필요할 때는 셸 권한이 `all`이어야 `.env`의 서비스키를 읽는다. 키는 문서와 로그에 남기지 않는다. 경로 안의 `20260925`를 연도 치환으로 바꾸지 않는다.

원천:

- 서울 구간·통과조 API 보관: `data/research/seoul_api4_3_sections_20260926/{sections|corner_rank}/{year}/page_0001.json`, 요청 기록은 `request_ledger.jsonl`
- 부산 구간 API 보관: `data/research/busan_api4_3_sections_20260925/raw/{2017..2026}/page_0001.json`. 부산 착순은 `bu*Ord`다. 같은 응답의 `sj*Ord`는 0이라 쓰지 않는다
- 부산·제주 2025–2026 통과조 API는 적재 때 실시간으로 읽었고 별도 JSON으로 남기지 않았다
- 성적표 원문: `data/raw/kra_text/dacom11/meet={1|2|3}/year=YYYY/**/*.rpt`, cp949. 서울·제주 라벨은 `S-1F`, `C1`–`C4`, `G-1F`다. 부산 라벨은 `S1F`, `G8F`, `G6F`, `G4F`, `G3F`, `G2F`, `G1F`다
- 공식 화면: `https://race.kra.co.kr/raceScore/ScoretableDetailList.do?Act=04&Sub=1&meet={1|2|3}&realRcDate=YYYYMMDD&realRcNo=N`

2017–2024는 그 해의 dacom 경주 집합이 연구 DB 경주 집합과 같을 때만 통과조를 원문으로 갈아끼운다. 일부 날짜만 있으면 API에 있던 통과조를 유지한다. 서울 2026 dacom은 3일이라 갈아끼우지 않았다.

## 3. 경마장마다 성적표 칸이 다르다

확인일은 2026-09-26이다.

| 경마장 | 말별 통과착순 | 경주 통과조 | G3F |
|---|---|---|---|
| 서울 | `S1F-1C-2C-3C-G3F-4C-G1F` | `S-1F`, 1·2·3·4코너, `G-1F` | 착순은 누적 행. 통과조에는 없다. `3F-G`는 막판 시간 |
| 부산 | `S1F-G8F-G6F-G4F-G3F-G2F-G1F` | `S-1F`, `G8F`, `G6F`, `G4F`, `G3F`, `G2F`, `G-1F` | 착순과 통과조 모두 있다. 짧은 거리는 앞 지점이 빈다 |
| 제주 | `S1F-1C-2C-3C-4C-G1F` | `S-1F`, 1·2·3·4코너, `G-1F` | 착순도 통과조도 없다. `G-3F`는 막판 시간. 옆의 `3F 0:00.0`은 경주 펄롱 시간 |

dacom 말별 착순 줄은 서울이 여섯 칸(`S1F-1C-2C-3C-4C-G1F`)이라 화면의 G3F 숫자를 빠뜨린다. 그래서 운영 DB 서울 G3F 착순이 비어 있었다. 화면의 G3F 착순은 API `sjG3fOrd`이고, 누적 시간 `seG3fAccTime`과 한 쌍이다. 이 착순을 막판 G3F 행에 붙이지 않는다.

제주 연구 시트는 제주마만이다. 등급이 `제`이거나, 2018-08-25까지의 구형 숫자 등급이다. `한` 한라마는 넣지 않는다. `horses.origin_country`로 과거 경주를 나누지 않는다.

통과조 열 대응:

| 경마장 | API `corner_*` | 지점 |
|---|---|---|
| 서울·제주 | 1, 2, 3, 4, 7, 8 | 1C, 2C, 3C, 4C, S1F, G1F |
| 부산 | 1, 2, 3, 5, 7, 8, 9 | G8F, G6F, G4F, G3F, S1F, G2F, G1F |

서울 2020–2021은 이 대응이 인쇄 성적표와 어긋난다. 2020-01-05 3경주는 인쇄된 G-1F가 API `corner_1`에 들어가 있다. 그 두 해는 보관된 API 열을 다시 복사하지 않고 dacom 라벨을 썼다. 2017–2019와 2022–2026 서울은 이 대응이 성적표와 맞다.

## 4. 연구 DB에 지금 들어 있는 것

통과조가 있는 경주 수 / 성적표 경주 수. 2026-09-26에 연구 DB를 다시 세었다.

서울·제주 통과조의 G3F 행은 0이다. 제주 G3F 착순도 0이다. 부산 막판·구간 행의 착순은 0이다. 부산 착순은 누적 행에만 있다.

서울 2017–2024 G3F는 막판 행을 그대로 두고, `time_kind=cumulative`, `source_name=api4_3` 행을 추가했다. 2025–2026 서울 G3F는 이미 누적이었고 API와 불일치 0이었다. 2017년 1,000m로 보면 막판 G3F는 34.7–45.3초, 누적 G3F는 23.2–28.4초다.

서울에서 API와 달랐는데 덮어쓰지 않은 G3F 외 착순은 2017년 33, 2018년 22, 2019년 17, 2020년 2, 2021년 51, 2022년 26, 2023년 72칸이다. 2022년에는 비어 있던 착순 10칸만 API로 채웠다. 예: 2017-12-02 12경주 켄터키연인 S1F는 DB 2, API 4. 사용자가 유지하라고 해서 그대로 두었다.

제주 S1F·3C·4C·G1F 착순은 기존 연구 DB 값을 유지했다. 2C 착순은 긴 거리 일부만 있다. 2026년 272/397, 2025년 380/524, 2024년 98/404다. 없는 칸을 만들지 않는다.

## 6. 통과조가 비어 있는 경주

성립하지 않은 경주라 성적표 통과 칸이 비어 있다. 값을 만들지 않았다.

부산은 2025-12-26 6경주 하나다. [성적표](https://race.kra.co.kr/raceScore/ScoretableDetailList.do?Act=04&Sub=1&meet=3&realRcDate=20251226&realRcNo=6)는 출발대 내 11번 하운드포커가 진입하지 않은 상태에서 출발하여 경주불성립이라고 적는다. 9번 스타포스는 출발 준비 중 방마로 출전제외다. 12두 착순·구간·통과조가 비어 있다. 같은 날 나머지 경주에는 통과조가 있다.

제주 2025년 7경주는 짙은 안개로 경주취소다.

| 날짜 | 경주 | 성적표 조치 | 연구 DB 착순 |
|---|---|---|---|
| 2025-05-03 | 4·5·6 | 5분 대기 후에도 안개가 호전되지 않아 경주취소 | 전원 99 |
| 2025-05-09 | 7 | 시야 확보가 어려워 5분 대기 후 경주취소 | 전원 99 |
| 2025-05-24 | 2 | 같은 5분 대기 후 경주취소. 10번 탐라의빛은 왼 앞다리 절음으로 출전제외 | 1–9번 99, 10번 94 |
| 2025-12-13 | 6 제주일마배 | 대상경주라 10분 대기 후 경주취소 | 12두 공백 |
| 2025-12-20 | 6 | 5분 대기 후 경주취소 | 8두 공백 |

12월 두 경주는 성적표 문구가 경주취소인데 연구 DB와 운영 DB 착순은 99가 아니라 공백이다. 5월 3일·9일과 12월 13일·20일에는 전개 기호가 있다. 5월 24일 2경주만 전개 기호가 없다.

제주 2026년 빈 20경주는 취소일이다. 2026-03-20 1–8경주, 2026-03-21 1–6경주, 2026-04-04 1–6경주. 착순은 99다. 이 20경주는 API에도 통과조가 없다.

이 사유는 [성적표 DB 2025 경주 절](MEET_SCORE_AND_TRIAL_DB_2026-09-25.md), [CURRENT_STATUS](CURRENT_STATUS.md)의 2025 R6 공백, [DATA_AND_OPERATIONS](DATA_AND_OPERATIONS.md)의 같은 항목에 반영했다.

## 7. 살아있는 문서와 다른 곳

[성적표 DB](MEET_SCORE_AND_TRIAL_DB_2026-09-25.md) 29절은 아직 “2017년 통과조가 비어 있다”고 적혀 있다. 그 문장은 이번 적재 전 상태다. 2017년 통과조는 서울 4,858줄·1,094경주, 부산 4,277줄·805경주, 제주 2,044줄·552경주다. 2절의 시간 종류 설명도 서울 2017–2024에 추가한 누적 G3F 행을 아직 말하지 않는다. 연도별 표의 통과조 칸은 2025·2026 수치와는 맞고, 2017–2024 본문은 적재 전 설명과 섞여 있다. 통과조 유무와 G3F 착순은 이 인수인계의 4절을 본다.

운영 `race_section_results`는 `(race_entry_id, section_code)`라 `time_kind`가 없다. 누적 G3F와 막판 G3F를 그 테이블에 함께 넣지 않는다. 웹은 아직 그 운영 테이블을 읽는다. 사용자는 운영 DB와 웹 교체를 보류했다.

## 8. 다음에 하지 말 것

- 서울 G3F 외 착순 불일치 33·22·17·2·51·26·72칸을 API 값으로 덮어쓰지 않는다. 사용자가 유지하기로 했다.
- 서울·제주 통과조에 G3F를 만들지 않는다. 제주 G3F 착순도 만들지 않는다.
- 부산 막판·구간 행에 착순을 붙이지 않는다. 부산 착순은 `bu*Ord`다.
- 2020–2021 서울 통과조를 API `corner_rank`로 되돌리지 않는다.
- 안개 취소·경주불성립·2026 제주 취소 경주의 빈 통과조를 채우지 않는다.
- 한라마를 제주 연구 시트에 넣지 않는다.
- 운영 DB, Supabase, 모델, 예측 원장, 웹 구간 조회를 이번 연구 시트로 바꾸지 않는다.
- 2016년 이전 성적표는 사용자가 만들기 전에는 착수하지 않는다.
- 커밋은 사용자가 요청할 때만 한다.
