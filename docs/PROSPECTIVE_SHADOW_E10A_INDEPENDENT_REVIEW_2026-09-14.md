# E10-A 준비표 독립 검토

결정: **준비표 승인, 실제 실행 승인 아님**. `waiting_for_publication_evidence`는 읽은 로컬 자료에 부합한다. 현재 외부 게시 상태는 이번 검토에서 확인하지 않았다.

입력 24개와 준비표·상태 JSON 2개의 SHA256, 총 26개를 재계산해 불일치 0건이다. data/experiments 아래 capture_journal.jsonl 세 파일에서 요청 레코드 2+3+2=7건과 ack 7건을 확인했다. ack를 별도 전송으로 세지 않았다. 최초 2건은 ConnectError, 이후 5건은 HTTP 200이다. 기록상 잔여는 5회이며 기록 밖 전송의 부재까지 입증하지 않는다.

기존 runner 103행의 `BudgetTransport(..., limit=12)`는 실행마다 상한을 초기화한다. 116–124행은 정상 출전표 뒤 두 번째 전체 batch를 자동 수집한다. 따라서 새 준비표의 누적 예산·일정 1 batch→출전표 1 batch 계약으로 실행하려면 별도 실행 경로가 필요하다. 기존 사례 margin 계산도 출전표 ack만 전달하므로 새 경로에서는 준비표대로 두 원천 완료 ack의 최댓값을 명시적으로 사용해야 한다. 이는 기존 실제 사례의 시간 위반을 입증한 것이 아니다. 기존 미래 사례는 0건이다.

준비표 자체를 다시 작성하거나 과거 실험을 반복할 필요는 없다. 다음 범위는 기존 수집 부품을 재사용하는 한 번짜리 실행부의 offline 구현·합성 검증이다. 공식 게시 근거 확인은 별도 외부 조건이다. 두 조건이 충족되어야 실제 수집 지시로 넘어간다.

실제 F_t 적격, 실제 feature snapshot 연결, 후향 A 136열 모델의 전향 적격은 이번 승인에 포함되지 않는다. E9 봉인 평가도 그대로 보존한다. HTTP·학습·추론·결과 조회 0회. 코드 변경 없이 문서와 검토 로그만 추가했으므로 pytest는 재실행하지 않았다.
