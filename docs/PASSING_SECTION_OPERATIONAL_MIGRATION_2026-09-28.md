## 결론

## 구 테이블 중복과 전환 결과

`race_section_results`의 원래 2,448,057행 중 새 성적표 지점과 겹친 행은 1,115,251행이었다. 웹 경주 상세·과거 분석·모델 특성 조회는 새 원천을 우선하고, 같은 말·지점에 새 원천이 없을 때만 구 테이블을 읽도록 바꿨다. 막판 G3F/G1F 시간이 있으면 시간값으로 우선 사용하고, 통과착순은 누적 행에서 우선 읽는다. 수집기는 성적표가 있는 말의 구 구간 행을 다시 넣지 않는다. 기존 테이블을 그대로 읽도록 두고 삭제하면 화면·모델 조회가 깨지기 때문에 이 선행 변경이 필요했다.

로컬에서는 중복 행 1,115,251개를 5,000행씩 삭제해 구 테이블 1,332,806행을 보존했다. `race_passing_summaries`는 전체 행과 경주 페이스·3F/4F 기록을 유지하고, 새 통과조와 같은 지점인 기존 문자열 필드만 89,843개 비웠다. 모델용 유효 구간 조회 집계는 삭제 전후 모두 2,921,106행, 시간 합계 107,078,388,600ms, 착순 합계 14,044,748이었다. 서울 2026-09-20 1경주 경주 상세는 삭제 전후 모두 11두와 같은 구간 컬럼을 표시했고, 6번 말의 막판 600m·200m는 36.6초·12.3초로 같았다. 로컬 `PRAGMA quick_check`는 `ok`, `foreign_key_check`는 0건이다. 물리적인 SQLite 파일 크기는 삭제 직후 자동으로 줄지 않는다.

로컬 데이터 상태 화면의 새 성적표 원천 최신일은 2026-09-20, 원천 미커버 구 테이블의 최신일은 2016-12-31이다. 2017년 이후 동일 말·지점의 중복은 0건이다. 관련 DB·웹·분석·수집 테스트 118개가 통과했다.

Supabase 삭제 전 구 테이블 2,448,057행과 통과 요약 19,952행 전체를 압축 CSV로 로컬에 보관하고, 행 수·압축 파일 SHA-256을 검증했다. 사용자 지시에 따라 배포보다 먼저 원격의 중복 구간 1,115,251행을 5,000행씩 삭제하고 통과조와 중복되는 구 문자열 필드 89,843개를 비웠다. 원격 구간 구 테이블은 1,332,806행, 중복은 0행이며 로컬과 같다. 통과 요약 19,952행과 경주 페이스·3F/4F 필드, 2000-01-08~2016-12-31 구 원천 전용 구간은 보존했다. 삭제 직후 원격 DB 논리 크기는 약 4,387 MB로 삭제 전 약 4,373 MB보다 오히려 커졌으며, PostgreSQL의 삭제가 디스크 할당을 즉시 줄이지 않는 점에 유의한다.

삭제 후 원격과 로컬의 구 구간·통과 요약에 대해 행 수뿐 아니라 ID 합, 참조 ID 합, 시간·착순 합, 남은 통과 문자열 길이 합도 일치했다. 새 구간시간의 시간 합계 62,736,733,500ms·착순 합계 7,128,012, 통과조 문자열 길이 합계 2,973,846도 동일하다. 양쪽 DB의 새·구 구간 외래키 고아는 원격에서 0건으로 확인했다. 압축 백업은 `gzip -t` 검사에 통과했고, 삭제 후에도 로컬 백업 디렉터리에 보존한다.

Cloud Run의 마지막 확인 설정은 2026-09-23 생성된 `mapilog-00018-mq4` 구 이미지에 트래픽 100%, ingress `internal`이다. 이는 인스턴스가 실제 실행 중인지와 별개다. **구 이미지는 새 조회 코드를 포함하지 않으므로 재가동하거나 요청을 받기 전에 새 revision 배포·검증이 필요하다.** 이번 작업에서 Cloud Run 배포·트래픽 변경은 하지 않았다.

삭제 후 새 코드를 Supabase DB에 읽기 전용으로 연결한 경주 상세 검증은 성공했다. 서울 2026-09-20 1경주, 부산 2026-09-18 1경주, 제주 2026-09-19 1경주, 구 원천 전용 부산 2016-12-31 1경주의 경주 상세와 분석·데이터 상태 조회가 로컬과 일치했다. 서울 표본의 막판 600m 36.6초·200m 12.3초도 같다. 새 DB 조회 코드 자체는 원격에서도 작동하지만 Cloud Run 배포가 끝난 것은 아니다.

실제 중복 행 비교에서도 부산 2017–2024의 구 테이블 `S1F` 무시간종류 행 61,114개가 새 누적값·착순과 일치하지 않았다. 예를 들어 부산 2017-12-31 14경주에는 구 운영값과 API 기반 새 원천값에 1초 차이가 나는 행들이 있다. 새 원천을 우선하는 결정은 맞지만, 기존 모델 입력을 조용히 바꾸거나 라이브 웹 기록을 비우는 방식으로 삭제해서는 안 된다. `race_passing_summaries`에도 통과조와 별개인 경주 페이스·3F/4F 시간이 있어 테이블 전체 삭제는 불가하다.

모델 입력 의미 변화도 확인했다. 2025–2026 부산 G3F/G1F는 구 테이블이 누적 시간을 쓰던 행이 많고, 새 호환 조회는 막판 시간을 우선한다. 2025년 부산 G1F 7,905행 중 7,892행, G3F 7,905행 중 7,850행에서 선택된 시간 숫자가 다르다. 2026년에는 각각 5,800행 중 5,789행과 5,773행이 다르다. 반면 같은 기간 부산 S1F, 서울·제주·영천의 이 세 주요 지점은 해당 비교에서 값 차이가 0건이었다. 이 수치는 정확성 평가가 아니라 구 입력과 새 입력의 차이 건수다. 현재 등록된 더러브렛·제주 메인 예측 스크립트는 별도 연구 산출물을 읽어 이 운영 구간 테이블을 직접 사용하지 않지만, `analysis/features/base.py`를 사용하는 범용 모델 경로는 영향을 받으므로 별도 예측 회귀검증이 필요하다.

## 남은 원격 컷오버 순서

### 2026-09-28 로컬 전환 후 추가 검증

사용자 요청에 따라 Cloud Run 배포와 Supabase 중복 삭제는 보류하고 로컬만 재검증했다. 새 원천·구 원천 중복은 0건이며, 새 구간시간 1,823,443행·통과조 103,410행·구 원천 전용 구간 1,332,806행을 확인했다. SQLite `PRAGMA quick_check`는 `ok`, 외래키 오류는 0건이다. 구 원천 전용 기록의 범위는 2000-01-08~2016-12-31이며, 새 원천은 서울·부산·제주 2017년 이후와 영천 2026년을 포함한다.

실제 로컬 DB를 읽기 전용 연결로 사용한 웹 HTTP 확인에서 서울 2026-09-20 1경주, 부산 2026-09-18 1경주, 제주 2026-09-19 1경주, 구 원천으로 조회되는 부산 2016-12-31 1경주의 상세 페이지가 모두 HTTP 200이었다. 분석 화면과 데이터 상태 화면도 HTTP 200이었다. 서울 표본의 막판 600m·200m는 각각 36.6초·12.3초로 표시됐다. 관련 구간·통과·DB 테스트는 85개 통과했고, 변경 파일의 Ruff 검사도 통과했다.

전체 `pytest`는 **1,053개 통과·5개 실패**였다. 실패 5개는 이 전환 코드가 아니라 로컬에 없는 `confirmed_starter_e6a_v2_20260913_attempt4/artifact_manifest.json`, `confirmed_starter_e7a_20260913_attempt4/{artifact_manifest.json,sequence_features.parquet}`, `jeju_native_ablation_order_v6_20260916/protocol.json`을 요구하는 연구 테스트다. 해당 산출물을 생성하거나 기존 연구 파일을 임의 변경하지 않았다. 따라서 전체 테스트 100% 통과는 아직 주장할 수 없다. 새 원천을 사용하는 범용 예측 경로의 실제 예측값 회귀검증과 Cloud Run 새 revision 검증 역시 배포 전에 남아 있다.

로컬 검증 후 사용자 지시에 따라 Supabase 중복은 삭제했다. Cloud Run 배포는 계속 보류 중이다.

1. 현재 작업 트리의 무관한 변경 100여 개를 배포에 섞지 않도록 전용 변경분을 검토·분리한다. 배포는 Cloud Build/Run 비용과 운영 상태를 확인한 뒤 무트래픽 새 revision으로 먼저 진행한다.
2. 새 revision에서 경주 상세·분석·모델 특성 조회를 Supabase 새 원천으로 검증한다. 기존 모델 산출물은 자동 재학습하지 않는다. 과거 부산 S1F와 2025–2026 부산 G3F/G1F처럼 달라지는 입력은 범용 예측 결과에 영향을 줄 수 있으므로 별도 회귀검증이 필요하다.
3. **구 revision으로 서비스를 재개하지 않는다.** 새 revision이 원격 DB의 삭제 후 상태에서 정상 작동함을 확인한 다음 트래픽을 전환한다.
4. 재수집 방지, 웹, 예측 재검증과 DB 무결성·디스크 사용량을 확인한다. PostgreSQL 삭제는 공간을 즉시 OS에 반환하지 않고 재사용 가능한 공간을 만든다.

로컬·Supabase 중복 삭제는 완료, Cloud Run 배포는 미실행이다. 새 성적표 DB가 물리적으로 존재한다는 사실과, 공개 서비스가 새 코드를 실제로 사용한다는 사실을 혼동하지 말 것.
